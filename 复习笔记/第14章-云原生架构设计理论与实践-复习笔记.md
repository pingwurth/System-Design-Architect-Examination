# 第14章 云原生架构设计理论与实践 - 考前复习笔记

## 章节概述

云原生（Cloud Native）：Cloud = 应用软件在云端而非传统数据中心；Native = 从一开始就基于云环境设计，充分利用云平台弹性+分布式优势。

本章主线：背景 → 定义 → 架构原则 → 架构模式 → 反模式 → 关键技术（容器/微服务/无服务器/服务网格） → 案例分析。

---

## 14.1 云原生架构产生背景

### 演进路径

传统"烟筒"模式 → IaaS统一 → 敏捷开发（解决开发效率） → DevOps（打通开发与运维） → 云原生（容器/微服务技术支撑DevOps和持续交付）

### 核心驱动力

- 企业IT资源被大量占用且难以共享 → 需要统一复用
- 开发与运营"信息鸿沟" → 需要DevOps协同
- 高并发流量需求 → 需要快速弹性扩容
- 数字孪生体系构建 → 云原生成为新生产力工具

### 云原生在各领域的应用

| 领域 | 应用方式 |
|------|----------|
| **人工智能/大数据** | 容器化替换基础平台，更细粒度资源划分、更快扩容 |
| **边缘计算** | 解决轻量化、异构设备管理、海量应用运维难题 |
| **高性能计算（HPC）** | 科研、生物、制药等行业升级为云原生架构 |

## 14.2 云原生架构内涵

### 14.2.1 云原生架构定义 ⭐

> 云原生架构是基于云原生技术的一组架构原则和设计模式的集合，旨在将云应用中的**非业务代码部分进行最大化的剥离**，从而让云设施接管应用中原有的大量非功能特性（弹性、韧性、安全、可观测性、灰度等），使业务具备轻量、敏捷、高度自动化的特点。

**代码三部分**：

| 部分 | 说明 | 价值 |
|------|------|------|
| **业务代码** | 实现业务逻辑 | ✅ 核心价值 |
| **三方软件** | 业务代码依赖的三方库（业务库+基础库） | 附属 |
| **处理非功能特性的代码** | 高可用、安全、可观测性等 | 附属，可剥离到IaaS/PaaS |

### 三大影响 ⭐

**1. 代码结构发生巨大变化**
- 存储从"文件"变成"服务"（对象存储、块存储、文件存储）
- 云产品解决分布式挑战（高可用、自动扩缩容、安全、运维升级）
- 开发人员不再需要掌握复杂的文件/网络/分布式处理技术

**2. 非功能性特性大量委托**
- 功能性特性 = 真正为业务带来价值的代码
- 非功能性特性 = 高可用、容灾、安全、可运维性等（无直接业务价值但必不可少）
- 云产品在三个层面提供高可用方案：**虚拟机**（热迁移）、**容器**（异常节点自动替换）、**云服务**（无状态化 + 负载均衡）

**3. 高度自动化的软件交付**
- 容器以标准方式打包，屏蔽环境差异
- 基于容器做标准化软件交付
- 面向终态的交付过程（代码识别环境差异，自动完成安装/配置/运行/变更）

### 14.2.2 云原生架构原则 ⭐

| 原则 | 核心要点 |
|------|----------|
| **服务化原则** | 以应用模块为颗粒度拆分（微服务/小服务）；面向接口编程；标准化服务流量传输；限流降级/熔断隔仓/灰度等基于**服务流量**控制 |
| **弹性原则** | 部署规模随业务量自动伸缩；无须事先容量规划；降低闲置成本；保障突发扩张 |
| **可观测原则** | 主动通过**日志、链路跟踪、度量**等手段使服务调用可见；下钻到SQL/网络/节点拓扑；实时掌握运行状况 |
| **韧性原则** | 抵御异常的能力（硬件故障、资源瓶颈、流量超限、攻击等）；核心目标：提升**MTBF**（平均无故障时间）；包括：异步化、重试/限流/降级/熔断/反压、主从/集群、AZ高可用、单元化、跨region容灾、异地多活 |
| **所有过程自动化原则** | IaC（Infrastructure as Code）、GitOps、OAM、Kubernetes Operator；标准化+自动化交付和运维 |
| **零信任原则** ⭐ | 默认不信任任何人/设备/系统；基于认证和授权重构访问控制；以**身份为中心**（非网络中心）；IP/主机/地理位置不能作为可信凭证 |
| **架构持续演进原则** | 不是封闭式架构；考虑组织层面架构治理和风险控制；存量应用迁移需权衡迁出/迁入成本和风险 |

### 14.2.3 主要架构模式 ⭐

#### 1. 服务化架构模式

- 以应用模块为颗粒度划分软件
- 以**接口契约（IDL）** 定义业务关系
- 以**标准协议（HTTP、gRPC等）** 确保互联互通
- 结合DDD、TDD、容器化部署
- 典型模式：**微服务**（细粒度）和**小服务**（关系密切的服务组合，共享数据，适用于超大型系统）
- 注意：拆分导致维护模块增多，缺乏自动化和治理能力反而降低效率

#### 2. Mesh化架构模式

- 将中间件框架（RPC、缓存、异步消息等）从业务进程中分离
- 业务进程只保留很"薄"的Client
- 流量控制、安全等逻辑由**Mesh进程**完成
- 收益：分布式架构模式（熔断、限流、降级等）无需三方软件包；零信任架构能力；流量动态环境隔离

#### 3. Serverless模式

- 将"部署"从运维中"收走"
- 开发者不关心运行地点、OS、网络、CPU
- 业务流量到来时云启动/调度业务进程，完成后自动关闭

**不适用场景**：
- 有状态应用（调度可能导致上下文丢失）
- 长时间后台运行的密集型计算
- 频繁外部I/O（网络/存储/服务间调用）

**适用场景**：事件驱动的数据计算任务、计算时间短的请求/响应、没有复杂相互调用的长周期任务

#### 4. 存储计算分离模式

- 无状态应用 → 获得好的A（可用性）和P（分区容错性）→ 更好的弹性
- 推荐将暂态数据（session）、结构化/非结构化持久数据都采用云服务
- 状态太大时 → 采用**时间日志+快照（检查点）** 方式实现快速增量恢复

#### 5. 分布式事务模式 ⭐

| 模式 | 一致性 | 性能 | 侵入性 | 特点 |
|------|--------|------|--------|------|
| **XA** | 强一致 | 差 | 低 | 传统方案 |
| **BASE（消息最终一致）** | 最终一致 | 高 | 低 | 通用性有限 |
| **TCC** | 可控 | 较高 | **强** | 设计开发维护成本高 |
| **SAGA** | 可控 | 较高 | **强** | 无try阶段，正向事务对应补偿事务 |
| **SEATA AT** | 高 | **高** | **无** | 自动回滚，有使用场景限制 |

#### 6. 可观测架构

三个方面：
- **Logging**：多级别详细信息跟踪（verbose/debug/warning/error/fatal）
- **Tracing**：完整调用链路跟踪（前端到后端）
- **Metrics**：系统量化多维度度量

关键：定义清晰的**SLO**（Service Level Objective），包括并发度、耗时、可用时长、容量等。

#### 7. 事件驱动架构（EDA）

事件 vs 传统消息：事件具有**schema**（可校验有效性），具备**QoS保障机制**。

应用场景：

| 场景 | 说明 |
|------|------|
| **增强服务韧性** | 异步集成，下游失败不影响上游 |
| **CQRS** | 命令用事件发起，查询用同步API |
| **数据变化通知** | 订单完成 → 积分/信用服务更新 |
| **构建开放式接口** | 事件提供者不关心订阅者 |
| **事件流处理** | 大量事件流数据分析（如Kafka日志处理） |
| **IoT事件触发** | 传感器数据天然适合EDA |

### 14.2.4 典型反模式 ⭐

| 反模式 | 问题 |
|--------|------|
| **庞大的单体应用** | 缺乏依赖隔离；代码耦合；模块接口缺乏治理；一个子模块不稳定影响整体；只能整体扩容 |
| **单体"硬拆"为微服务** | 小规模强行拆分导致发布维护成本增加；服务间共享数据库导致数据耦合；本地调用变分布式调用性能急剧下降 |
| **缺乏自动化能力的微服务** | 模块数量增多但缺乏自动化 → 人均工作量增大、发布时间变长、运维风险提升 |

## 14.3 云原生架构相关技术

### 14.3.1 容器技术 ⭐

#### 背景与价值

- **Docker**：基于操作系统虚拟化，共享OS内核、轻量、秒级启动
- **Docker镜像**：解耦应用与运行环境 → 应用分发工业标准
- **Kubernetes**：容器编排事实标准，屏蔽IaaS层差异

#### 三大核心价值

| 价值 | 说明 |
|------|------|
| **敏捷** | 3~10倍交付效率提升 |
| **弹性** | 充分发挥云计算弹性优势，降低50%计算成本 |
| **可移植性** | CNCF一致性认证，不同K8s实现兼容 |

#### Kubernetes核心能力

| 能力 | 说明 |
|------|------|
| **资源调度** | 根据CPU/Memory/GPU选择合适节点 |
| **应用部署与管理** | 自动发布、回滚、配置管理、存储卷编排 |
| **自动修复** | 监测宿主机故障，自动迁移/自愈 |
| **服务发现与负载均衡** | Service资源 + DNS + 多种负载均衡机制 |
| **弹性伸缩** | 监测负载，自动扩容 |

#### Kubernetes控制平面四组件 ⭐

1. **APIServer** —— API入口
2. **Controller** —— 控制器
3. **Scheduler** —— 调度器
4. **etcd** —— 分布式存储

关键特性：
- **声明式API**：关注应用自身而非执行细节（Deployment/StatefulSet/Job等资源类型）
- **可扩展性架构**：CRD/Operator扩展
- **可移植性**：Load Balance Service/CNI/CSI屏蔽底层差异

### 14.3.2 云原生微服务 ⭐

#### 微服务设计约束

**1) 微服务个体约束**
- 业务域划分相互独立
- 不同业务域有不同技术选择权
- "两张披萨饼"团队规模 / "两周完成一次迭代"
- 按**问题域**合理拆分，不是为微而微
- 遵循**单一职责原则（SRP）**

**2) 微服务横向关系**
- **可发现性**：服务注册中心（推送和扩展能力关键）
- **可交互性**：与语言无关的远程调用协议（REST标准化 / 基于IDL的二进制协议高性能场景）
- 元数据中心存储服务元数据
- 增强韧性：限流、熔断、隔仓、负载均衡
- 提升吞吐：协程、Rx模型、异步调用、反压

**3) 微服务与数据层纵向约束**
- **数据存储隔离（DSS）**：数据是微服务私有资产，访问必须通过API
- **读写分离（CQRS）**
- **无状态设计原则**：上层应用与基础设施解耦
- 有状态微服务 → 计算与存储分离，数据下沉到分布式存储

**4) 全局分布式约束**
- 全自动化CI/CD流水线
- 支持蓝绿、金丝雀发布策略
- 全链路、实时、多维度可观测能力
- 中心化监控系统

#### 主要微服务技术

| 技术 | 来源 | 特点 |
|------|------|------|
| **Apache Dubbo** | 阿里巴巴 | 高性能RPC框架；智能负载均衡、自动服务注册发现 |
| **Spring Cloud Alibaba** | 阿里巴巴 | 分布式应用框架；含Nacos（注册/配置中心）、Sentinel（流控）、Seata（分布式事务） |
| **Spring Cloud** | 社区 | 配置管理、服务发现、断路器、智能路由等全套能力 |
| **Eclipse MicroProfile** | Eclipse | Java微服务规范；指标/API文档/健康检查/容错/分布式跟踪 |
| **Tars** | 腾讯 | 多语言（C++/Java/Golang/Node.js/PHP）；兼顾易用性和高性能 |
| **SOFAStack** | 蚂蚁金服 | 金融级分布式架构中间件 |
| **DAPR** | 微软 | 分布式应用运行时；可移植、无服务器、事件驱动 |

### 14.3.3 无服务器技术（Serverless） ⭐

#### 技术特点

| 特征 | 说明 |
|------|------|
| **全托管计算服务** | 只需编写代码，无需关注服务器运维 |
| **通用性** | 结合BaaS API支撑各类应用 |
| **自动弹性伸缩** | 无需提前容量规划 |
| **按量计费** | 无需为闲置资源付费 |

**FaaS（Function as a Service）**：Serverless最具代表性的产品形态
- 事件驱动方式触发执行
- 弹性且高可用

**FaaS面临的困难**：
1. 编程方式变化（事件驱动）→ 架构/习惯/流程大改
2. 生态不够成熟
3. 冷启动导致响应延迟、按需建连成本高

**新型Serverless形态**：与容器技术融合（弹性容器实例ECI、Serverless应用引擎SAE、CloudRun、Knative）

#### 技术关注点

**1) 计算资源弹性调度**

放置算法目标：
- **容错**：多实例分布在不同节点和可用区
- **资源利用率**：混合调度不同类型应用，动态迁移碎片整理
- **性能**：复用启动过的节点、利用缓存加速
- **数据驱动**：离线分析验证在线调度效果

**2) 负载均衡和流控**
- 资源调度服务分片 → 横向扩展
- 多租户环境下流量隔离保证服务质量

**3) 安全性**
- 权限管理、网络安全、数据安全、运行时安全
- **轻量安全容器**：更小隔离粒度、更快启动、更小开销

### 14.3.4 服务网格（Service Mesh） ⭐

#### 技术特点

- 将微服务间的连接、安全、流量控制、可观测等通用功能**下沉为平台基础设施**
- **无侵入方式**实现应用轻量化（无需修改业务代码）
- 数据平面（代理截获请求）+ 控制平面（配置策略）

**Istio主要组件**：

| 组件 | 职责 |
|------|------|
| **Pilot** | 服务发现、流量管理 |
| **Mixer** | 访问控制、可观测性 |
| **Citadel** | 终端用户认证、流量加密 |

额外开销：多4个IPC通信成本，但对百毫秒级业务调用影响 < 2%。

#### 协议标准化趋势

- **Envoy**：数据平面事实标准（Google/IBM/Cisco/Microsoft/阿里云共建）
- **xDS协议**：数据平面与控制平面间标准协议
- **SMI（Service Mesh Interface）**：更高层次抽象
- **UDPA（Universal Data Plane API）**：基于xDS扩展
- **Wasm技术**：插件隔离 + 多语言支持
- 安全：与零信任架构天然结合（mTLS链路加密、RBAC/ACL、微隔离）

#### 主要服务网格技术对比

| 技术 | 数据平面 | 控制平面 | 特点 |
|------|----------|----------|------|
| **Istio** | Envoy | Go | 功能最完整；基于Kubernetes；主流方案 |
| **Linkerd** | Rust (linkerd-proxy) | Go | 时延/资源消耗优于Istio；功能不如Istio完整 |
| **Consul** | 可选Envoy | Consul Server | 功能不如Istio完整 |
| **Conduit** | Rust | Go | 超轻量级；最快最轻最安全；倾向K8s低资源部署 |

## 14.4 案例分析要点

### 案例1：某旅行公司云原生改造

**三阶段改造**：
1. **第一阶段**：系统合并收拢到云原生私有云平台；资源虚拟化封装切割；解决Java GC资源争抢（JVM升级 + Kata Container）
2. **第二阶段**：服务稳定性保障；声明式API + 不可变基础设施 + 服务网格 + 容器服务；弹性计算 + Scale Zero
3. **第三阶段**：基础组件云原生改造；跨地域跨云自动化灾备；DevOps演进

**效益**：订单业务使用40%机器支撑全线服务；单机资源利用率提升20%；弹性支撑300%峰值流量

### 案例2：某汽车公司数字化转型

**关键策略**：
- 容器云平台承载核心应用（多租户弹性计算）
- 私有云+公有云混合交付（按敏态/稳态特性部署）
- 微服务拆分形成业务中台
- DevOps贯穿始终

**效益**：应用交付周期从2个月缩短到1个月

### 案例3：某快递公司核心业务上云

**架构转型**：Vmware+Oracle → **Kubernetes云原生架构**

关键改造：
- 引入云原生数据库（OLTP + OLAP分离）
- 应用容器化（解决环境不一致）
- 微服务改造（按业务域拆分）
- 最终方案："阿里云ACK+神龙+云数据库"

### 案例4：某电商业务云原生改造

**关键产品组合**：ACK容器服务 + Spring Cloud Alibaba + PTS（性能测试）+ AHAS（高可用）+ 链路追踪

### 案例5：某体育用品公司业务中台

**核心问题**：63套烟囱系统、30余家IT供应商、T+1数据回传、高库存+高缺货

**解决方案**：全渠道业务中台（商品/渠道/库存/订单/营销/用户/结算中心）

**效益**：售罄率提升8%、缺货率降低12%、周转率提升20%、80%前台应用运行在中台之上

## 高频考点速记

1. **云原生定义** ⭐ —— 最大化剥离非业务代码，让云设施接管非功能特性
2. **七大架构原则** ⭐ —— 服务化、弹性、可观测、韧性、自动化、零信任、持续演进
3. **七大架构模式** ⭐ —— 服务化、Mesh化、Serverless、存储计算分离、分布式事务、可观测、事件驱动
4. **五种分布式事务模式** ⭐ —— XA/BASE/TCC/SAGA/SEATA AT的对比
5. **Kubernetes四组件** ⭐ —— APIServer/Controller/Scheduler/etcd
