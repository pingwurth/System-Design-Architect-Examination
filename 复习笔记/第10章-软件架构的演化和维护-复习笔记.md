# 第10章 软件架构的演化和维护 - 考前复习笔记

## 章节概述

本章围绕软件架构**全生命周期中的变化管理**展开。核心逻辑：演化是什么（概念）→ 怎么演化（面向对象操作）→ 何时演化（静态/动态分类）→ 如何可持续演化（18条原则）→ 演化效果如何评估 → 大型网站演化实例 → 如何维护。考试重点集中在**演化分类（静态vs动态）、面向对象演化操作、18条原则、DSA动态架构、网站架构十阶段**。

## 10.1 软件架构演化和定义的关系

### 10.1.1 演化的重要性 ⭐

**核心观点：软件架构是演化来的，而不是设计来的。**

演化目的：维持软件架构自身的**有用性**，涵盖架构全生命周期（需求获取→建模→文档→实现→维护）。

演化重要的三个原因：
1. 架构是系统骨架，支撑性能/可靠性/安全性/易维护性
2. 架构提供宏观蓝图，基于架构的检测和修改成本较低
3. 架构演化保证演化的**一致性和正确性**，降低成本

**架构便于演化的三个原因：**
- 形式化、可视化表示提高了**可构造性**
- 架构设计涵盖的结构/配置/约束信息有助于考虑未来演化
- 组件间耦合描述有助于**动态调整**

### 10.1.2 演化和定义的关系 ⭐

**SA = {组件(Components), 连接件(Connectors), 约束(Constraints)}**

| 要素 | 演化内容 | 波及效应 |
|------|---------|---------|
| **组件** | 模块的增加/删除/修改 | 增加→新交互消息；删除→删除已有消息；改变→改变已有消息 |
| **连接件** | 组件交互消息的增加/删除/改变 | 伴随模块改变，或因内部结构调整导致交互流程改变 |
| **约束** | 知识库中仿真数据的增加/删除/改变 | 可能是架构约束数据或参数的变化 |

> **变更元素分类：** 受变更**直接影响**的元素 + 受变更**波及**的元素 + 不受影响的元素 = 演化后的软件架构

## 10.2 面向对象软件架构演化过程 ⭐

基于UML顺序图讨论四种演化操作。

### 10.2.1 对象演化

| 操作 | 缩写 | 说明 |
|------|------|------|
| **AddObject** | AO | 添加新对象（增加新功能或将功能独立化） |
| **DeleteObject** | DO | 删除对象（移除功能或合并对象降低复杂度） |

> **关键理解：** 对象属性（接口、类型、语义）的演化不影响交互过程。只有AO/DO才对架构动态行为产生影响。孤立对象（无交互关系）的演化对系统无意义，一般伴随消息演化。

### 10.2.2 消息演化 ⭐⭐

消息是顺序图的**核心元素**，消息演化是顺序图演化的**核心**。

| 操作 | 缩写 | 说明 |
|------|------|------|
| **AddMessage** | AM | 增添新消息（增加交互行为） |
| **DeleteMessage** | DM | 删除消息（移除交互行为），AM的逆操作 |
| **SwapMessageOrder** | SMO | 交换两条消息的时间顺序 |
| **OverturnMessage** | OM | 反转消息的发送/接收对象 |
| **ChangeMessageModule** | CMM | 改变消息的发送或接收对象 |

**消息演化与约束的关系（三类）：**
1. **与约束无关** → 不影响正确性/时态属性（如多数AM）
2. **关联但不违背约束** → 不影响正确性（如CMM后仍满足约束）
3. **关联且违背约束** → **不正确**的演化（如DM删除了约束内容中的消息）

### 10.2.3 复合片段演化

复合片段 = 对象交互关系的**控制流描述**，与消息同属**连接件**范畴。

产生分支的复合片段类型：ref、loop、break、alt、opt、par

| 操作 | 缩写 | 说明 |
|------|------|------|
| **AddFragment** | AF | 新增复合片段（增添新控制流） |
| **DeleteFragment** | DF | 删除复合片段（移除控制流），AF的逆操作 |
| **FragmentTypeChange** | FTC | 改变片段类型（交互流程改变，可视为删除+添加组合） |
| **FragmentConditionChange** | FCC | 改变内部执行条件（同时修改符合/不符合条件的两个转移） |

> **注意：** 复合片段演化对应交互流程变化，可能违背约束，需要**验证**。

### 10.2.4 约束演化

| 操作 | 缩写 | 说明 |
|------|------|------|
| **Add Constraint** | AC | 添加新约束，需判断设计是否满足新约束 |
| **Delete Constraint** | DC | 移除约束，一般架构会满足演化后的约束 |

> 约束修改 = 删除原有约束 + 添加新约束。约束缺乏可视化描述，信息不存储于层次自动机中。

## 10.3 软件架构演化方式的分类 ⭐⭐

### 三种分类方法

| 分类维度 | 类别 |
|---------|------|
| **实现方式和实施粒度** | 基于过程/函数 → 面向对象 → 基于组件 → 基于架构 |
| **研究方法**（Jeffrey M. Barnes） | ①对演化的支持 ②版本/工程管理工具 ③架构变换形式方法 ④成本收益分析 |
| **是否处于系统运行时期** | **静态演化** vs **动态演化** ⭐ |

### 10.3.1 演化时期 ⭐

| 时期 | 英文 | 发生阶段 | 特点 |
|------|------|---------|------|
| **设计时演化** | Design-Time | 模型/代码编译之前 | 最自由 |
| **运行前演化** | Pre-Execution | 编译之后、执行之前 | 不考虑应用状态，需有添加/删除组件机制 |
| **有限制运行时演化** | Constrained Runtime | 运行中，特定约束满足时 | "安全"模式下执行规定操作 |
| **运行时演化** | Runtime | 运行中，架构不满足要求时 | **最难实现** |

### 10.3.2 静态演化 ⭐⭐

**两类需求：**
1. 设计时演化需求（开发实现过程中调整架构）
2. 运行前演化需求（发布后因环境变化修改升级）

**静态演化五个步骤（必记顺序）：**
1. **软件理解** — 查阅文档、分析架构、识别元素和关系
2. **需求变更分析** — 找出新需求与原有需求的差异
3. **演化计划** — 确定范围/成本，选择计划
4. **系统重构** — 按计划重构以适应需求
5. **系统测试** — 测试演化后的系统

**维护三类：** 更正性维护、适应性维护、完善性维护

**原子演化操作：** 基于UML模型，逻辑语义上**粒度最小**的架构修改操作。每次操作产生一个中间版本 Ai。

#### 与可维护性相关的原子操作 ⭐

| 操作 | 缩写 | 说明 |
|------|------|------|
| Add Module Dependence | AMD | 增加模块间依赖 |
| Remove Module Dependence | RMD | 删除模块间依赖 |
| Add Module Interface | AMI | 增加模块间接口 |
| Remove Module Interface | RMI | 删除模块间接口 |
| Add Module | AM | 增加模块 |
| Remove Module | RM | 删除模块 |
| Split Module | SM | 拆分模块 |
| Aggregate Modules | AGM | 聚合模块 |

#### 与可靠性相关的原子操作 ⭐

| 操作 | 缩写 | 说明 |
|------|------|------|
| Add Message | AMS | 顺序图中增加交互消息 |
| Remove Message | RMS | 顺序图中删除交互消息 |
| Add Object | AO | 顺序图中增加交互对象 |
| Remove Object | RO | 顺序图中删除交互对象 |
| Add Fragment | AF | 顺序图中增加消息片段 |
| Remove Fragment | RF | 顺序图中删除消息片段 |
| Change Fragment | CF | 顺序图中修改消息片段 |
| Add Use Case | AU | 用例图中增加可执行用例 |
| Remove Use Case | RU | 用例图中删除可执行用例 |
| Add Actor | AA | 用例图中增加参与者 |
| Remove Actor | RA | 用例图中删除参与者 |

#### 正交软件架构（静态演化实例）

**特点：** 功能分层+线索化，同一层次组件不允许相互调用，每个变动仅影响一条线索。

**演化过程五步：**
1. 需求变动归类（对应组件/线索，判断重用）
2. 制订架构演化计划
3. 修改/增加/删除组件
4. 更新组件间相互作用
5. 产生演化后的软件架构

### 10.3.3 动态演化 ⭐⭐

**两类需求来源：**
1. 软件内部执行导致的架构改变（如创建新组件响应用户）
2. 外部请求对软件的重配置（如OS运行时升级）

#### 软件动态性三级（Cuesta分类）⭐

| 级别 | 名称 | 含义 | 支持程度 |
|------|------|------|---------|
| 1 | **交互动态性** | 数据在固定结构下动态交互 | 广泛支持 |
| 2 | **结构动态性** | 允许组件/连接件实例的添加和删除 | 研究主流 |
| 3 | **架构动态性** | 允许基本构造变动（如新组件类型定义） | 支持甚少，但Cuesta认为只有此级别才是真正动态架构 |

#### 动态演化四方面内容

| 方面 | 说明 |
|------|------|
| 属性改名 | 运行时重定义非功能属性（如响应时间） |
| 行为变化 | 更换算法/协议/组件重新配置 |
| 拓扑结构改变 | 增删组件/连接件，改变关联关系 |
| 风格变化 | 变为衍生风格（如两层C/S → 三层C/S） |

#### DSA（动态软件架构）⭐⭐

**定义：** 运行时刻会发生变化的体系结构，可修改自身架构并在执行期间进行修改。

**DSA实现基本原理：**
- 架构以有状态、有行为、可操作的实体显式表示，被运行环境共享
- 架构信息改变 → 触发/驱动系统动态调整 → 调整结果反映在架构层面
- 引入**运行时体系结构对象**，分离协同逻辑与计算组件（关注分离原则）

**DSA实施四步：**
1. 捕捉并分析需求变化
2. 获取或生成演化策略
3. 选择并实施演化策略
4. 演化后评估与检测

**DSA必须提供的功能：**
- 保存当前架构信息（拓扑结构、组件状态/数目）
- 监控管理机制（监视需求变化、分析可否/何时/范围演化）
- 保证演化操作**原子性**（失败则撤销整个操作集）

#### DSA描述语言 ⭐

| 语言 | 视角 | 原理 | 适用场景 |
|------|------|------|---------|
| **π-ADL** | 行为视角 | 进程代数（π演算），组件/连接件/行为随时间演化 | 移动系统（动态连接关系） |
| **Pilar** | 反射视角 | 反射理论，元系统描述感知/修改，基系统提供应用操作 | 架构反射 |
| **LIME** | 协调视角 | Linda扩展，分离计算和协调，时空因素分离 | 分布式/移动应用 |

**反射模型关键概念：**
- **MARMOL**（Meta Architecture Model）：第一个将反射和架构结合的形式化模型
- 元系统 vs 基系统：元系统描述如何感知/修改自身，基系统提供常规操作
- Pilar中组件四部分：接口、配置、具化(Reification)、约束

#### DSA演化工具

| 方法 | 代表 |
|------|------|
| 反射机制 | K-Component框架、PKUAS（RSA）、SASM、Artemis-ARC |
| 组件操作 | 基于组件的动态体系结构模型、SACDRE |
| π演算 | SAAM（软件体系抽象模型） |
| 外部管理器 | ArchStudio（Argo图形 + ArchShell文本 + 扩展向导脚本） |

#### PKUAS实例

PKUAS是符合Java EE规范的组件运行支撑平台，四类实体：
1. **容器系统** — 组件生命周期管理（类装载、实例化、缓存、释放）
2. **公共服务** — 非功能性约束（通信/安全/事务），通过微内核动态增删
3. **工具** — 部署工具（热部署）、配置工具、实时监控工具
4. **微内核** — 系统组件装载/配置/卸载/状态管理，符合JMX标准

#### 动态重配置（DR）

四类重配置模式：

| 模式 | 原理 | 特点 |
|------|------|------|
| **主从模式** | 主组件分配工作给从组件，合并响应 | 从组件空闲时等待激活 |
| **中央控制模式** | 中央控制器控制多个组件 | 广泛用于实时系统 |
| **客户端/服务器模式** | 客户端请求，服务器响应，通过同步消息交互 | 事务完成后可增删组件 |
| **分布式控制模式** | 功能整合在分布式控制组件中 | 含环形模式和顺序模式 |

**动态重配置四个难点：**
1. 约束定义困难
2. 性能约束难以静态衡量，需运行时评估
3. 单方案难以管理所有方面
4. 需同时保证组件系统完整性 + 重配置策略正确安全性

## 10.4 软件架构可持续演化原则（18条）⭐⭐

> 考试中常以选择题/填空题出现，需记住原则名称、核心含义和度量方案。

### 成本/进度/风险类

| # | 原则 | 核心思想 | 度量方案 |
|---|------|---------|---------|
| 1 | **演化成本控制(ECC)** | 演化成本远小于重新开发成本 | CoE << CoRD |
| 2 | **进度可控** | 演化在预期时间内完成 | ttask = \|Ttask - T'task\|，越小越好 |
| 3 | **风险可控** | 经济/时间/人力/技术/环境风险在可控范围 | 分别检验各类风险不存在 |

### 结构/稳定性类

| # | 原则 | 核心思想 | 度量方案 |
|---|------|---------|---------|
| 4 | **主体维持** | 演化平均增量增长保持平稳 | AIG = 主体规模变更量/主体规模 |
| 5 | **系统总体结构优化** | 演化后整体布局更合理 | 检查可靠性和性能指标 |
| 6 | **平滑演化(IWR)** | 演化速率趋于稳定 | IWR = 变更总量/项目规模 |
| 7 | **目标一致** | 阶段目标与最终目标一致 | otask = \|Otask - O'task\|，越小越好 |

### 模块/影响类

| # | 原则 | 核心思想 | 度量方案 |
|---|------|---------|---------|
| 8 | **模块独立演化（修改局部化）** | 模块演化相互独立或影响最小 | 修改是否局部化 |
| 9 | **影响可控** | 模块变更影响范围可预测 | 影响范围是否可控 |
| 10 | **复杂性可控** | 架构复杂性在可控范围 | CC < 某个阈值 |

### 重构/重用类

| # | 原则 | 核心思想 | 度量方案 |
|---|------|---------|---------|
| 11 | **有利于重构** | 演化后更便于重构 | 检查复杂度（越复杂越不易重构） |
| 12 | **有利于重用** | 维持或提高可重用性 | 内聚度高 + 耦合度低 |

### 技术/标准/质量类

| # | 原则 | 核心思想 | 度量方案 |
|---|------|---------|---------|
| 13 | **设计原则遵从性** | 不与架构设计原则冲突 | RCP = \|CDP\|/\|DP\|，越小越好 |
| 14 | **适应新技术(TI)** | 独立于特定技术 | TI = 1 - DDT，DDT = \|依赖技术\|/\|用到技术\| |
| 15 | **环境适应性** | 容易适应新硬/软件环境 | 兼容性指标 |
| 16 | **标准依从性** | 不违背相关质量标准 | 人工判定 |
| 17 | **质量向好(QI)** | 演化后质量指标变好 | EQI ≥ SQ |
| 18 | **适应新需求** | 容易适应新需求变更 | RNR = \|ANR\|/\|NR\|，越小越好 |

## 10.5 软件架构演化评估方法 ⭐

### 10.5.1 演化过程已知的评估

**评估流程：**
1. 将完整演化拆分为**原子演化操作序列**
2. 每次原子操作产生中间版本 Ai，形成序列 A0, A1, ..., An
3. 对每个中间版本进行度量，得到质量属性值 Qi
4. 计算相邻版本间的**质量属性距离** D(i-1, i)
5. 综合评估

**可维护性距离公式：**

Dm(A,B) = 各指标归一化差值的笛卡儿距离（6个子指标的归一化笛卡儿距离）

**可靠性距离公式：**

Dr(A,B) = |a - b|/(a + b)

**关键结论：**
- 距离值越大 → 质量属性差距越大
- 质量属性距离**不具有累加性**：D(0,n) ≠ D(0,1) + D(1,2) + ...
- 应针对**同一架构的不同演化版本**度量，不同软件间比较无意义

### 10.5.2 演化过程未知的评估

**方法：** 根据演化前后的度量结果**逆向推测**架构发生了哪些改变。

**流程：**
1. 对演化前后版本分别度量
2. 计算质量属性距离
3. 逆向推测可能的演化操作及其位置/对象
4. 分析高层驱动原因（修复错误/提高性能/平台移植等）
5. 判断影响是否符合预期

## 10.6 大型网站架构演化实例（十阶段）⭐⭐

> 高频考点，常以选择题考察各阶段核心技术和解决的问题。

| 阶段 | 架构 | 核心技术 | 解决的问题 |
|------|------|---------|-----------|
| **1** | **单体架构** | 所有资源在一台服务器 | — |
| **2** | **垂直架构** | 应用/文件/数据库分离（3台服务器） | 并发和存储不足 |
| **3** | **缓存** | 本地缓存 + 分布式远程缓存 | 数据库访问压力 |
| **4** | **服务集群** | 负载均衡调度 + 应用服务器集群 | 单一应用服务器瓶颈 |
| **5** | **数据库读写分离** | 主从热备 + 读写分离 | 数据库负载压力 |
| **6** | **反向代理 + CDN** | CDN（运营商机房）+ 反向代理（中心机房） | 区域差异导致访问速度差异 |
| **7** | **分布式文件系统 + 分布式数据库** | 分布式存储 | 单机存储不够（业务分库优先） |
| **8** | **NoSQL + 搜索引擎** | 非关系数据库 + 非数据库查询 | 数据存储/检索需求复杂化 |
| **9** | **业务拆分** | 按产品线拆分应用，独立部署 | 业务场景复杂 |
| **10** | **分布式服务** | 提取共用业务独立部署 | 应用复杂度指数增长、DB连接不足 |

**关键知识点：**
- CDN和反向代理基本原理都是**缓存**
- 分布式数据库是**最后手段**，优先使用业务分库
- 二八定律：80%访问集中在20%数据上
- 第10阶段通过**分布式服务**解决连接数为服务器规模**平方**的问题

## 10.7 软件架构维护 ⭐

架构维护 = 对演化过程进行**追踪和控制**，保障演化满足需求。

### 10.7.1 知识管理

**架构知识 = 架构设计 + 架构设计决策**（不仅记录方案，还要记录为什么这样做）

**知识管理困难的原因：**
- 文档化和维护的好处看似不大而成本较高
- 利益相关者更关注短期兴趣
- 开发者被创造性工作吸引，不愿反思设计决策
- 缺乏培训
- 即使文档化，知识也不能在组织中充分分享

### 10.7.2 修改管理

**核心做法：** 建立**隔离区域（Region of Quiescence）**，保障区域内修改对其他部分影响最小甚至无影响。需明确修改规则、修改类型、影响范围和副作用。

### 10.7.3 版本管理

为架构演化的版本控制、使用和评价提供依据，为量化度量奠定基础。

**相关技术：**
- 邻接矩阵和可达矩阵分析静态演化波及效应
- 动态语义网络模型 + 不动点浸润过程收敛判定
- 邻接矩阵原子过滤概念

### 10.7.4 可维护性度量 ⭐

**六个子度量指标：**

| 指标 | 缩写 | 含义 | 计算 |
|------|------|------|------|
| 圈复杂度 | **CCN** | 独立执行路径条数 | (totalE - totalN) + 2L |
| 扇入扇出度 | **FFC** | 组件调用/被调用频率 | CCN × ((E+W)×(X+R))² |
| 模块间耦合度 | **CBO** | 模块间交互频繁程度 | (E+X+W+R)/totalN |
| 模块响应 | **RFC** | 执行所需功能数量 | S+E+R |
| 紧内聚度 | **TCC** | 模块内紧密耦合程度 | (E+X+W+R)/P(S) |
| 松内聚度 | **LCC** | 模块内松散耦合程度 | (E+X+W+R+NC(S))/P(S) |

> **CCN ≤ 10** 为宜。CCN高的程序最容易出错。
>
> CBO越大 → 可维护性越差，风险越高。
>
> 高内聚 + 低耦合 = 好的架构设计。

## 高频易混淆对比

### 静态演化 vs 动态演化

| 维度 | 静态演化 | 动态演化 |
|------|---------|---------|
| 时机 | 系统**停止运行**期间 | 系统**运行**期间 |
| 难度 | 较低 | **更高** |
| 需求来源 | 用户需求变化/运行环境变化/运行出错 | 内部执行导致架构改变 + 外部重配置请求 |
| 对应时期 | 设计时 + 运行前 | 有限制运行时 + 运行时 |
| 本质 | 软件修复和升级 | 不停止系统完成演化 |

### DSA vs DR（动态重配置）

| 维度 | DSA（动态软件架构） | DR（动态重配置） |
|------|-------------------|-----------------|
| 关注点 | 架构本身的动态性 | 配置信息的动态修改 |
| 对应动态性级别 | **架构动态性**（级别3） | **结构动态性**（级别2） |
| 允许的变化 | 基本构造变动（新组件类型等） | 组件/连接件实例增删、连接关系修改 |

### 四种演化类型对比

| 类型 | 操作数量 | 核心 |
|------|---------|------|
| 对象 | 2（AO, DO） | 添加/删除交互实体 |
| 消息 | 5（AM, DM, SMO, OM, CMM） | 改变交互行为（**核心**） |
| 复合片段 | 4（AF, DF, FTC, FCC） | 改变控制流 |
| 约束 | 2（AC, DC） | 改变配置/约束条件 |

## 高频考点速记卡

- ⭐ 架构是**演化来的**，不是设计来的
- ⭐ SA三要素：组件 + 连接件 + 约束
- ⭐ 消息演化是顺序图演化的**核心**，5种操作
- ⭐ 静态演化五步：软件理解 → 需求变更分析 → 演化计划 → 系统重构 → 系统测试
- ⭐ 动态性三级：交互(1) < 结构(2) < 架构(3)
- ⭐ DSA实施四步：捕捉变化 → 生成策略 → 实施演化 → 评估检测
- ⭐ DSA描述语言：π-ADL(行为)、Pilar(反射)、LIME(协调)
- ⭐ 四种重配置模式：主从、中央控制、C/S、分布式控制
- ⭐ 大型网站十阶段：单体→垂直→缓存→集群→读写分离→CDN/反向代理→分布式→NoSQL→业务拆分→分布式服务
- ⭐ 架构知识 = 架构设计 + 架构设计**决策**
- ⭐ 修改管理核心：建立**隔离区域**
- ⭐ 可维护性6指标：CCN、FFC、CBO、RFC、TCC、LCC
- ⭐ 质量属性距离**不具累加性**
- ⭐ 正交架构：同层组件不相互调用，变动仅影响一条线索
