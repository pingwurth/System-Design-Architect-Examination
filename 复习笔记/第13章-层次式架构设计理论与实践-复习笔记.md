# 第13章 层次式架构设计理论与实践 - 考前复习笔记

## 章节概述

层次式架构（N层架构）是软件体系结构设计中最常用的架构形式。核心思想：将系统组织为层次结构，每一层为上层服务，并作为下层客户。典型分为四层：**表现层、中间层（业务层）、数据访问层（持久层）、数据层**。

核心特性：**关注分离**（Separation of Concerns）——每层组件只负责本层逻辑。

---

## 13.1 层次式体系结构概述

### 软件体系结构定义

> 软件体系结构为软件系统提供了结构、行为和属性的高级抽象，由构成系统的元素描述、元素的相互作用、指导元素集成的模式以及这些模式的约束组成。

三个考察维度：
1. **利益相关人员之间的交流** —— 系统抽象是各方沟通的基础
2. **系统设计的前期决策** —— 最早的架构决策，影响后续开发、部署和维护
3. **可传递的系统级抽象** —— 可跨系统复用，促进大规模软件复用

### 层次式架构关键特性

- 每层最多影响两层（上层和下层）
- 内部层接口只对相邻层可见（精选的输出函数除外）
- 连接件通过层间交互协议定义
- 只要提供相同接口，允许每层用不同方法实现

### 两个设计注意事项

| 问题 | 说明 |
|------|------|
| **污水池反模式** ⭐ | 请求简单穿过几层，基本没做业务逻辑。用二八原则判断：超过20%的请求如此则应让某些层变成"开放的" |
| **应用膨胀** | 分层可能带来分布模式复杂、健壮性下降、可靠性/性能不足、代码规模膨胀 |

## 13.2 表现层框架设计

### 13.2.1 表现层设计模式 ⭐

#### MVC 模式

- **Model（模型）**：业务数据和业务逻辑，一个模型可为多个视图提供数据
- **View（视图）**：用户界面，显示数据、接收输入，**不进行业务处理**，可向模型查询但**不能改变模型**
- **Controller（控制器）**：接受用户输入，调用模型和视图完成需求；是用户界面与Model的接口

流程：Controller接收请求 → 调用Model处理业务逻辑 → Model返回数据 → Controller调用View格式化呈现

优点：
1. 允许多种用户界面扩展（视图与模型无必然联系）
2. 易于维护（公共接口保持不变）
3. 功能强大的用户界面

#### MVP 模式

- **Model**：提供数据
- **View**：负责显示
- **Presenter**：负责逻辑处理（对应MVC的Controller）

**核心区别**：View和Model**不能直接通信**，所有交互通过Presenter进行。Presenter依赖抽象化的View（IView接口），使UI处理逻辑**易于测试**。

优点：
1. 模型与视图**完全分离**
2. 所有交互集中在Presenter内部，更高效
3. 一个Presenter可用于多个视图
4. **脱离用户接口进行单元测试**

主要应用：**Android开发**

#### MVVM 模式

- **Model**：数据模型
- **View**：用户界面
- **ViewModel**：视图模型（核心），通过**DataBinding**实现View与Model的**双向绑定**

核心机制：
- ViewModel实现**观察者模式**，数据变化时通知View自动更新
- 用户操作View时，ViewModel监听变化并通知数据修改
- 形成**双向数据绑定**

适用场景：**数据驱动场景**，数据操作特别频繁

缺点：双向绑定导致问题定位困难（可能是数据问题或业务逻辑问题）

#### 三种模式对比 ⭐

| 对比项 | MVC | MVP | MVVM |
|--------|-----|-----|------|
| View与Model通信 | **可以直接通信** | **不能直接通信** | **不能直接通信** |
| 中间层角色 | Controller | Presenter | ViewModel |
| 数据绑定方式 | 无绑定 | 通过Presenter传递 | **DataBinding双向绑定** |
| 可测试性 | 一般 | **好**（依赖抽象View接口） | 一般 |
| 主要应用 | Java EE Web应用 | **Android** | 数据驱动场景 |
| 核心特点 | 关注分离 | 模型视图完全分离 | 双向数据绑定 |

### 13.2.2 XML设计表现层

- 用XML描述GUI控件（位置、类型、事件等作为XML节点属性）
- **策略模式**：装载XML配置 → 根据特定表现技术的解析器解析 → 得到GUI视图实例
- 优点：GUI只需维护一套XML文件，可转换为Web Form或Windows Form

### 13.2.3 UIP设计思想

**UIP（User Interface Process Application Block）**——微软开源框架

将表现层分为：
1. **User Interface Components**：用户看到和交互的界面
2. **User Interface Process Components**：协调界面各部分（导航、工作流控制、状态管理）

UIP负责：管理信息流、管理事务、修改流程响应异常、将交互流程从设备实现分离、保持事务关联状态

### 13.2.4 表现层动态生成

基于XML的界面管理技术三部分：
1. **界面配置**：静态定义，读取配置文件初始值
2. **界面动态生成**：通过DOM API读取XML + 数据库数据 → 运行时动态生成界面
3. **界面定制**：运行过程中用户可修改界面元素属性，运行结束保存结果

## 13.3 中间层架构设计

### 13.3.1 业务逻辑层组件设计

**组件结构**：接口 + 实现类

- **接口**：定义业务逻辑组件必须实现的方法，面向接口编程解耦
- **实现类**：以DAO组件为基础，通过Spring IoC/DI机制注入DAO组件
  - 实现类将DAO接口实例作为属性（面向接口编程）
  - 复杂业务调用多个DAO接口，将具体实现委派给DAO

**配置要点**：
- 使用事务代理模板，将业务逻辑组件作为嵌套bean配置
- 避免直接调用没有事务特性的业务逻辑组件
- Web层仅依赖Facade接口 → 松散耦合

### 13.3.2 业务逻辑层工作流设计 ⭐

**工作流定义**（WFMC）：业务流程的全部或部分自动化，文档、信息或任务按照过程规则流转。

**工作流参考模型5个接口**：

| 接口 | 名称 | 功能 |
|------|------|------|
| Interface 1 | 过程定义导入/导出 | 转换格式和API调用，支持过程定义互转（WPDL → XPDL） |
| Interface 2 | 客户端应用程序 | 工作流机与任务表处理器交互 |
| Interface 3 | 应用程序调用 | 工作流机直接激活应用工具（后台服务为主） |
| Interface 4 | 工作流机协作 | 不同厂商工作流系统间无缝任务传递（4个协同模型） |
| Interface 5 | 管理和监视 | 用户/角色/审查/资源/过程管理 |

优点：应用逻辑与过程逻辑分离，通过修改过程模型改变系统功能。

### 13.3.3 业务逻辑层实体设计

**业务逻辑层实体特点** ⭐：
- 提供对业务数据及功能状态的编程访问
- 可使用来自多个相关表的复杂数据构建
- 可作为业务过程的I/O参数传递
- **可以是可序列化的**（本地磁盘、桌面数据库、消息队列存储）
- **不直接访问数据库**（由数据访问逻辑组件提供）
- **不启动事务处理**（由使用实体的应用程序或业务过程启动）

**实体表示方式对比**：

| 方式 | 优点 |
|------|------|
| **XML** | W3C标准、灵活性（层次+集合）、互操作性（跨平台交换） |
| **通用DataSet** | 灵活、序列化、数据绑定、排序过滤、XML互换、开放式并发、可扩展 |
| **有类型DataSet** | 代码易读、IntelliSense支持、**编译时类型检查** |

### 13.3.4 业务逻辑层框架

**Domain Model—Service—Control 思想** ⭐：

| 组件 | 职责 |
|------|------|
| **Domain Model** | 领域层业务对象，仅包含业务相关**属性** |
| **Service** | 业务过程实现，不同功能单元通过中立接口和契约联系（**松耦合**） |
| **Control** | 服务控制器，根据Domain Model状态和参数决定Service执行顺序及关系 |

互动关系：
- Service依赖Domain Model状态，也可改变其状态
- Control根据状态和参数决定Service执行顺序

业务容器（Business Container）方式存在 → 降低与相邻层耦合，防止业务层代码渗透到表示层。

## 13.4 数据访问层设计

### 13.4.1 五种数据访问模式 ⭐

| 模式 | 特点 |
|------|------|
| **在线访问** | 最基本、最常用；占用数据库连接持续交互 |
| **DAO** | 标准J2EE模式；分离底层数据访问与高层业务逻辑；包含：DAO工厂类、DAO接口、具体实现类、DTO |
| **DTO** | 经典EJB模式；跨进程/网络边界传输数据的容器；不包含业务逻辑；两种实现：内置集合对象 vs 自定义类 |
| **离线数据模式** | 以数据为中心；操作独立于连接/事务；与XML集成；独立于数据源 |
| **ORM** | 对象/关系映射；将数据库记录与对象互转；降低SQL编写 |

### 13.4.2 工厂模式在数据访问层应用

- 定义数据库访问接口（DataAccess）
- 实现抽象类（AbstractDataAccess）+ 各数据库具体实现类
- **DataAccessFactory**：根据数据库类型返回适当的数据访问类
- 数据库切换只需修改PersistenceProperty值，客户端无感知

### 13.4.3 ORM、Hibernate与CMP2.0 ⭐

**ORM核心思想**：在关系型数据库和对象之间做映射，操作数据库如同操作对象。

ORM优势：
- 降低学习/开发成本
- 减少重复DAL代码
- 通过Cache调优性能
- 隔离数据存储和业务层

**Hibernate**：
- 开源ORM框架，对JDBC轻量级封装
- 提供Java类到数据表的映射 + 数据查询和恢复机制
- 利用代理模式简化数据提取
- 支持几乎所有流行数据库服务器
- 轻型体系（应用提供JDBC连接）vs 全面解决体系（抽象所有JDBC/JTA API）

### 13.4.4 XML Schema

- 描述XML文档合法结构、内容和限制
- 由XML 1.0自描述，使用命名空间
- 逐步替代DTD

**三部分规范**：
1. **Part0: Primer** —— 非标准化文档，简单可读描述
2. **Part1: Structures** —— Schema定义语言
3. **Part2: Datatypes** —— 数据类型定义方法

**XML Schema vs DTD**：丰富数据类型、支持继承、与Namespace紧密联系

### 13.4.5 事务处理设计 ⭐

**ACID原则**：

| 特性 | 含义 |
|------|------|
| **A（Atomicity）原子性** | 事务中任何失败导致所有修改失效 |
| **C（Consistency）一致性** | 失败时数据恢复到事务执行前状态 |
| **I（Isolation）隔离性** | 事务提交前修改对其他事务不可见 |
| **D（Durability）持久性** | 已提交数据在事务失败后状态正确 |

**J2EE三种事务类型**（不要同时使用/嵌套）：
1. **JDBC事务**：`setAutoCommit(false)` → 执行SQL → `commit()`/`rollback()`
2. **JTA事务**：`UserTransaction.begin()` → 执行SQL → `commit()`/`rollback()`
3. **容器管理事务**

JTA三个主要接口：**UserTransaction**（事务划分）、**TransactionManager**（上下文管理）、**Transaction**

### 13.4.6 连接对象管理设计 ⭐

**连接池模式**（资源池模式的应用）：
- 系统初始化时创建静态连接池
- 请求连接时：有空闲连接 → 分配并标记；无空闲 → 复用已分配连接
- 释放连接时：无使用者 → 放回连接池（非关闭）

## 13.5 数据架构规划与设计

### 数据库设计与类设计融合
- 类和类关系的正确识别是数据模型关键
- 目标：最小化整个生存期花费（非仅开发费用）
- 建模是艺术，不存在唯一正确模型

### 数据库设计与XML设计融合

**XML文档分类**：
- **数据文档**：结构规则、同构、少混合内容（存储/传输Web数据）
- **文档文档**：结构不规则、零散、多混合内容（网页发布/邮件等）

**XML存储方式对比**：

| 方式 | 特点 |
|------|------|
| **基于文件** | 原始文本存储；需附加索引；无法获取结构化数据；查询返回原始文档 |
| **数据库存储** | 管理方便、空间小、检索快、效率高、安全好；可操作内部数据；支持并发控制 |

XML作为数据库的局限：存储、索引、安全、多用户访问、事务管理等方面不足。适用于数据量少、用户少、性能要求低的场景。

## 13.6 物联网层次架构设计 ⭐

### 三层架构

| 层次 | 功能 | 类比 | 关键技术 |
|------|------|------|----------|
| **感知层** | 识别物体、采集信息（传感器、二维码、RFID、GPS等） | 皮肤和五官 | 检测技术、短距离无线通信 |
| **网络层** | 传递和处理信息（通信网+互联网融合） | 神经中枢和大脑 | 长距离有线/无线通信、网络技术 |
| **应用层** | 广泛智能化（与行业需求结合） | 社会分工 | 智能计算、云计算 |

应用层分类：**监控型**（物流/污染监控）、**查询型**（智能检索/远程抄表）、**控制型**（智能交通/智能家居）、**扫描型**（手机钱包/ETC）

应用层两个子层：
1. **应用程序层**：数据处理（电力、医疗、银行、交通等）
2. **终端设备层**：人机接口

## 13.7 案例分析要点

### PetShop（网上商店）

**版本演进**：
- **2.0**：无明显数据访问层 → 业务逻辑与数据访问职责混乱
- **3.0**：数据访问逻辑独立成层
- **4.0**：延续3.0结构 + 引入缓存和异步处理 + ASP.NET MemberShip

数据访问层模块：
- **IDAL**（接口）：抽象数据访问逻辑，脱离具体数据库依赖
- **DALFactory**：管理DAL对象创建
- **SQLServerDAL / OracleDAL**：实现IDAL接口的具体数据库操作
- **Model**：数据实体对象

关键设计：**面向接口编程** → 松散耦合 → 有利于数据库迁移

业务逻辑层（BLL）通过IDAL接口调用数据访问层，与具体数据访问逻辑无关。

### 电子小票物联网系统
- 感知层：小票智能硬件（STM32 + TFTLCD + Flash + 无线模块）
- 网络层：Wi-Fi/GPRS传输 → 云平台存储 → 服务支撑
- 应用层：云平台小票服务（微信推送） + 云平台数据服务（经营数据管理）
