### 1.1.1 系统架构的定义及发展历程

#### 1. 系统架构的定义

> 系统架构（System Architecture）是系统的一种整体的高层次的结构表示，是系统的骨架和根基，支撑和链接各个部分，包括组件、连接件、约束规范以及指导这些内容设计与演化的原理，它是刻画系统整体抽象结构的一种手段。

**架构 vs 结构的区别（易混淆考点）**

| 对比维度 | 架构 (Architecture) | 结构 (Structure) |
|----------|---------------------|------------------|
| **定义** | 体现在组件中的系统基本组织、彼此关系与环境关系，及指导设计和发展的原则（IEEE 1471-2000） | 系统中软件构件、构件的外部可见属性以及它们之间的相互关系（Bass, Clements, Kazman） |
| **抽象层次** | **高层次**的整体抽象表示，是系统的"骨架和根基" | **较低层次**的具体组成关系描述 |
| **包含内容** | 组件 + 连接件 + 约束规范 + **设计原则和演化指导** | 构件 + 外部可见属性 + 相互关系 |
| **关注点** | 系统的整体组织、设计决策和演化方向 | 构件如何组装、交互的具体方式 |
| **核心差异** | 架构包含结构，还包含**为什么这样组织**的原则和约束 | 结构只是架构的一个组成部分，不包含设计原理 |
| **比喻** | 建筑设计图（含设计理念、规范要求） | 建筑的框架结构（梁柱墙的排列方式） |

> **关键记忆点**：架构 > 结构。架构 = 结构 + 约束 + 设计原则 + 演化指导。结构是架构的子集，架构通过结构来体现，但架构不仅仅是结构。

- **架构**是体现在**组件**中的 <u>一个系统的基本组织</u>、<u>它们彼此的关系与环境的关系</u> 及 <u>指导它的设计和发展的原则</u>
- **系统**是组织起来完成某一特定功能或或一组功能的组件集。
  - 系统这个术语包括了单独的应用程序、传统意义上的系统、子系统、系统之系统、产品线、整个企业及感兴趣的其他集合。
  - 系统用于完成其环境中的一个或多个任务。
- **环境**或者上下文决定了对这个系统的开发、运作、政策以及会对系统造成其他影响的环境和设置。
- **任务**是由一个或者多个利益相关者通过系统达到一些目标的系统的一个用途或操作。

> 系统架构设计的目的是对需要开发的系统进行一系列相关的抽象，用于指导系统各个方面的设计与实现，架构设计在系统开发过程中起着关键性作用，架构设计的优劣决定了系统的健壮性和生命周期的长短。

架构设计的作用：
- 解决相对复杂的需求分析问题；
- 解决非功能属性在系统占据重要位置的设计问题；
- 解决生命周期长、扩展性需求高的系统整体结构问题；
- 解决系统基于组件需要的集成问题；
- 解决业务流程再造难的问题。

它不仅是连接用户需求和系统进一步设计与实现的桥梁，也是系统早期阶段质量保证的关键步骤。

##### 重要概念和定义

1. **软件架构（Software Architecture）**：软件系统的整体抽象结构，包括组件、连接件、约束规范以及指导这些内容设计与演化的原理
2. **模块化开发方法**：把一个待开发的软件分解成若干个小的而且简单的部分，采用对复杂事物分而治之的经典原则
3. **组件化技术**：具有可组装性和可插拔性，组件运行仅依赖于平台或容器，组件间无直接耦合关系
4. **SOA（面向对象服务架构）**：提供一组基于标准的方法和技术，通过有效整合和重用现有的应用系统和各种资源实现服务组件化
5. **软件产品线架构**：表示一组具有公共的系统需求集的软件系统，根据基本的用户需求对标准的产品线架构进行定制
6. **架构动态性**：软件系统在运行时刻的架构变化
7. **架构扩展**：架构的静态修改

##### 模块化设计原则（六大原则）

将系统分解成模块时，应该遵循以下规则：

1. **最高模块内聚**：在一个模块内部的元素最大限度地关联，只实现一种功能的模块是高内聚的，具有三种以上功能的模块则是低内聚的
2. **最低耦合**：不同模块之间的关系尽可能弱，以利于软件的升级和扩展
3. **模块大小适度**：颗粒过大会造成模块内部维护困难，而颗粒过小又会导致模块间的耦合增加
4. **模块调用链的深度不可过多**：嵌套层次不可过多
5. **接口简单、精炼**：扇入扇出数不宜太大，具有信息隐蔽能力
6. **尽可能地复用已有模块**

##### 架构风格分类（David Garland和Mary Shaw划分）

架构风格（架构模式）是针对给定场景中经常出现的问题提供的一般性可重用方案，它反映了领域中众多系统所共有的结构和语义特征。

**五类架构风格：**
1. 数据流风格
2. 调用/返回风格
3. 独立组件风格
4. 虚拟机风格
5. 仓库风格

##### 组件化技术要点

组件的特性：
- **可组装性**：组件可以与其他组件进行业务上的交互
- **可插拔性**：组件的运行仅依赖于平台或者容器
- **无直接耦合**：组件与组件之间不存在直接的耦合关系

组件化与相关概念的区别：
- **组件化 vs 模块化**：模块化开发只是在逻辑上做了切分，物理上(代码)通常并没有真正意义上的隔离；组件化比模块化更独立
- **组件化 vs 应用集成**：应用集成是将基于不同平台或不同方案的应用软件有机地集成到一个无缝的、并列的、易于访问的单一系统中；组件化比应用集成结合得更加紧密

##### 软件架构在软件生命周期中的影响

软件架构是软件生命周期中的重要产物，它影响软件开发的各个阶段：

1. **需求阶段**：把软件架构有的概念引入需求分析阶段，有助于保证需求规约和系统设计之间的可追踪性和一致性
2. **设计阶段**：设计阶段是软件架构研究关注最早、最多的阶段，主要包括软件架构的描述、软件架构模型的设计与分析以及对软件架构设计经验的总结与复用等
3. **实现阶段**：将设计阶段设计的算法及数据类型用程序设计语言进行表示，满足设计、架构和需求分析的要求
4. **维护阶段**：为了保证软件具有良好的维护性，需要对一些有关维护性的属性(如可扩展性、可替换性)进行规定

### 1.1.2 软件架构的常用分类及建模方法

#### 1. 软件架构的常用分类

多年来，“架构”概念经过不断演化，目前已形成了满足不同用途的架构模式。比较典型的架构模型包括以下五类：

| 架构类型 | 英文名称 | 核心特点 | 适用场景 |
|----------|----------|----------|----------|
| 分层架构 | Layered Architecture | 最常见的软件架构，事实上的标准架构 | 大多数企业应用、Web应用 |
| 事件驱动架构 | Event-driven Architecture | 通过事件进行通信 | 实时系统、消息处理系统 |
| 微核架构 | Microkernel Architecture | 又称为插件架构，内核相对较小 | 可扩展系统、IDE、浏览器 |
| 微服务架构 | Microservices Architecture | SOA的升级，每个服务独立部署 | 互联网应用、大型分布式系统 |
| 云架构 | Cloud Architecture | 解决扩展性和并发问题 | 云服务、高并发系统 |

##### 1) 分层架构（Layered Architecture）

**定义**：最常见的软件架构，也是事实上的标准架构。将软件分成若干个水平层，每一层都有清晰的角色和分工，不需要知道其他层的细节。

**四层结构**：
1. **表现层 (Presentation Layer)**：用户界面，负责视觉和用户互动
2. **业务层 (Business Layer)**：实现业务逻辑
3. **持久层 (Persistence Layer)**：提供数据，SQL语句就放在这一层
4. **数据库 (Database Layer)**：保存数据

**扩展说明**：有的项目在逻辑层和持久层之间加了一个服务层 (Service)，提供不同业务逻辑需要的一些通用接口。用户的请求将依次通过这四层的处理，不能跳过其中任何一层。

##### 2) 事件驱动架构（Event-driven Architecture）

**定义**：通过事件进行通信的软件架构。事件是状态发生变化时软件发出的通知。

**四个组成部分**：
1. **事件队列 (Event Queue)**：接收事件的入口
2. **分发器 (Event Mediator)**：将不同的事件分发到不同的业务逻辑单元
3. **事件通道 (Event Channel)**：分发器与处理器之间的联系渠道
4. **事件处理器 (Event Processor)**：实现业务逻辑，处理完成后会发出事件，触发下一步操作

**简化形式**：对于简单的项目，事件队列、分发器和事件通道可以合为一体，整个软件就分成事件代理和事件处理器两部分。

##### 3) 微核架构（Microkernel Architecture）

**定义**：又称为插件架构 (Plug-in Architecture)，是指软件的内核相对较小，主要功能和业务逻辑都通过插件实现。

**核心特点**：
- **内核 (Core)**：通常只包含系统运行的最小功能
- **插件**：互相独立，插件之间的通信应该减少到最低，避免出现互相依赖的问题

**典型应用**：IDE（如Eclipse）、浏览器（如Chrome）、操作系统（如微内核操作系统）

##### 4) 微服务架构（Microservices Architecture）

**定义**：服务导向架构 (Service-Oriented Architecture, SOA) 的升级。每一个服务就是一个独立的部署单元 (Separately Deployed Unit)。这些单元都是分布式的，互相解耦，通过远程通信协议(比如 REST、SOAP)联系。

**三种实现模式**：
1. **RESTful API模式**：服务通过API提供，云服务就属于这一类
2. **RESTful应用模式**：服务通过传统的网络协议或者应用协议提供，背后通常是一个多功能的应用程序，常见于企业内部
3. **集中消息模式**：采用消息代理 (Message Broker) 可以实现消息队列、负载均衡、统一日志和异常处理，缺点是会出现单点失败，消息代理可能要做成集群

##### 5) 云架构（Cloud Architecture）

**定义**：主要解决扩展性和并发的问题，是最容易扩展的架构。

**核心原理**：将数据都复制到内存中，变成可复制的内存数据单元，然后将业务处理能力封装成一个个处理单元 (Processing Unit)。若访问量增加，就新建处理单元；若访问量减少，就关闭处理单元。由于没有中央数据库，所以扩展性的最大瓶颈消失了。

**两大部分**：
1. **处理单元 (Processing Unit)**：实现业务逻辑
2. **虚拟中间件 (Virtualized Middleware)**：负责通信、保持会话控制、数据复制、分布式处理和处理单元的部署

**虚拟中间件的四个组件**：
1. **消息中间件 (Messaging Grid)**：管理用户请求和会话控制，当一个请求进来以后，它决定分配给哪一个处理单元
2. **数据中间件 (Data Grid)**：将数据复制到每一个处理单元，即数据同步，保证某个处理单元都得到同样的数据
3. **处理中间件 (Processing Grid)**：可选，如果一个请求涉及不同类型的处理单元，该中间件负责协调处理单元
4. **部署中间件 (Deployment Manager)**：负责处理单元的启动和关闭，监控负载和响应时间，当负载增加，就新启动处理单元，负载减少，就关闭处理单元

##### 架构分类对比分析

| 对比维度 | 分层架构 | 事件驱动架构 | 微核架构 | 微服务架构 | 云架构 |
|----------|----------|--------------|----------|------------|--------|
| **复杂度** | 低 | 中 | 中 | 高 | 高 |
| **扩展性** | 有限 | 良好 | 良好 | 优秀 | 最佳 |
| **耦合度** | 层间耦合 | 事件耦合 | 插件耦合 | 服务解耦 | 单元解耦 |
| **适用规模** | 中小型 | 中型 | 中型 | 大型 | 超大型 |
| **技术栈** | 相对统一 | 可混合 | 可混合 | 可混合 | 可混合 |
| **部署方式** | 整体部署 | 整体部署 | 模块化部署 | 独立部署 | 动态部署 |

#### 2. 系统架构的常用建模方法

根据建模的侧重点不同，软件架构的模型分成**4种**：结构模型、框架模型、动态模型和过程模型。

| 模型类型 | 核心特点 | 研究重点 |
|----------|----------|----------|
| **结构模型** | 最直观、最普遍的建模方法；以构件、连接件等概念刻画结构 | 反映系统的配置、约束、隐含假设条件、风格和性质；核心是**架构描述语言** |
| **框架模型** | 与结构模型类似，但不侧重细节，更侧重整体的结构 | 以特殊问题为目标建立只针对和适应问题的结构 |
| **动态模型** | 对结构或框架模型的补充 | 研究系统的"大颗粒"行为性质，如系统的重新配置或演化；常是**激励型**的 |
| **过程模型** | 研究构造系统的步骤和过程 | 其结构是遵循某些过程脚本的结果 |

> 4种模型并不是完全独立的，通过有机结合才可形成一个完整的模型来刻画软件架构。

**"4+1"视角模型（Philippe Kruchten，1995年）**

"4+1"模型从**5个不同视角**描述软件架构，每个视角只关心系统的一个侧面，5个视角结合在一起才能反映系统软件架构的全部内容：

| 视角 | 英文名称 | 关注点 |
|------|----------|--------|
| 逻辑视角 | Logical View | 系统的功能需求，系统向用户提供的服务 |
| 过程视角 | Process View | 系统的并发性、分布性、系统集成性和性能 |
| 物理视角 | Physical View | 系统的物理拓扑、通信、安装和部署 |
| 开发视角 | Development View | 系统在开发环境中的软件模块组织 |
| 场景视角 | Scenarios View | 将其他4个视角有机联系起来，用于验证和原型设计 |

**考试要点**：
- 选择题：4种建模模型的定义与区别；"4+1"模型的5个视角名称
- 案例分析题：根据需求选择合适的建模视角
- 论文写作题：多视角建模在大型系统中的应用

### 1.1.3 软件架构的应用场景

软件架构发展至今，已成为各个领域的关键技术能力。不同的架构风格具有各自的优缺点和应用场景：

| 架构风格 | 适用场景 | 典型应用 |
|----------|----------|----------|
| **管道-过滤器** | 将系统分成若干独立的步骤 | 编译器、数据处理流水线 |
| **主程序/子系统、面向对象** | 对组件内部进行设计 | 模块化系统、面向对象系统 |
| **虚拟机** | 构造解释器或专家系统 | 脚本解释器、专家系统 |
| **C/S和B/S** | 数据和处理分布在一定范围，通过网络连接构成系统 | Web应用、分布式系统 |
| **平台/插件** | 具有插件扩展功能的应用程序 | IDE、浏览器 |
| **MVC** | 用户交互程序的设计 | Web前端框架 |
| **SOA** | 企业集成 | 企业服务总线(ESB) |
| **C2** | GUI软件开发，构建灵活和可扩展的应用系统 | 图形界面应用 |

**现代大型软件的架构特点**：
- 很少使用**单一**的架构风格进行设计与开发
- 而是**混合多种风格**，从不同视角描述大型软件系统的能力
- 可保证软件系统的**可靠性**、**可扩展性**、**可维护性**等非功能属性的正确描述

**考试要点**：
- 选择题：各架构风格对应的典型应用场景（匹配题）
- 案例分析题：根据业务需求选择合适的架构风格
- 论文写作题：混合架构风格在大型项目中的实践

## 1.2 系统架构设计师概述

系统架构设计师（System Architecture Designer）是项目开发活动中的众多角色之一，可以是**一个人**、**一个小组**或**一个团队**。架构师（Architect）包含建筑师、设计师、创造者、缔造者等含义。

**架构师的分类（选择题考点）**

| 分类标准 | 类型 | 英文缩写 |
|----------|------|----------|
| **组织划分（5类）** | 业务架构师 | BA (Business Architect) |
| | 主题领域架构师 | DA (Domain Architect) |
| | 技术架构师 | TA (Technology Architect) |
| | 项目架构师 | PA (Project Architect) |
| | 系统架构师 | SA (System Architecture) |
| **微软分类（4种）** | 企业架构师 | EA (Enterprise Architect) |
| | 基础结构架构师 | IA (Infrastructure Architect) |
| | 特定技术架构师 | TSA (Technology Architect) |
| | 解决方案架构师 | SA (Solution Architect) |

### 1.2.1 架构设计师的定义、职责和任务

#### 1. 架构设计师的定义

> 架构设计师是负责系统架构的人、团队或组织（**IEEE 1471-2000**）。

**核心角色**：系统开发的主体角色，通过执行一系列活动来实施架构设计。架构设计通过生成过程形成最终的产品架构，架构设计师的成果是创建架构。

**架构设计师、架构设计与架构的关系**：
- 架构设计师 → 执行活动 → 架构设计 → 生成过程 → 产品架构
- 系统开发中**架构设计师是整个系统的核心**

**定义要点**：
- 系统或产品线的**设计责任人**
- 负责理解和管理并最终确认和评估**非功能性系统需求**（可维护性、性能、复用性、可靠性、有效性、可测试性等）
- 给出开发规范，搭建系统实现的核心构架
- 对整个软件架构、关键构件和接口进行总体设计
- 澄清关键技术细节的**高级技术人员**

#### 2. 架构设计师的职责

架构设计师的职责是**技术领导**，需要具备：

| 能力维度 | 具体要求 |
|----------|----------|
| **领导能力** | 体现在组织职位上：项目中的技术领导，拥有技术决策的权威 |
| | 体现在品质上：为他人树立榜样，在制定方向方面表现出自信 |
| | 以人为导向：指导并培养团队成员 |
| **专门技能** | 清楚项目总体目标和实施方法 |
| | 是特定开发平台、语言、工具的**大师** |
| | 对常见应用场景能及时给出最恰当的解决方案 |
| | 了解开发团队，评估实现特定功能需求的资源代价 |

**关键职责**：
- 关注交付的实际结果
- 赋予项目技术驱动力
- 能够进行决策并确保决策被传达、理解并始终被执行

**架构设计师与项目经理的关系**：
- 项目经理：关注管理资源、进度和成本
- 架构设计师：关注技术决策和架构设计
- 两者代表项目的公共角色

#### 3. 架构设计师的任务与组成

**三大任务**：
1. **领导与协调**整个项目中的技术活动（分析、设计和实施等）
2. **推动**主要的技术决策并最终表达为系统架构
3. **确定**系统架构，并促使其架构设计的文档化（包括需求、设计、实施和部署等"视图"）

**从技术角度看，三大职责**：
- **抽象设计**
- **非功能设计**
- **关键技术设计**

**团队组成**：
- 架构设计师角色可以由**一个人**或**一个团队**来履行
- 一个人可能会履行多个角色
- 架构设计师角色通常由**多个人**履行（技能广泛）
- 团队特征：拥有共同目标、可以相互负责、技能相互补充

**首席架构设计师的重要性**：
- 架构团队的单点协调人
- 具有先知先明的能力
- 没有这个协调人，架构团队难以创造出内聚的架构或做出决策

> **关键记忆点**：最优秀的架构通常由一个**团队**而不是个人创建，因为多人参与可以使见识更广和更深。

### 1.2.2 架构设计师应具备的专业素质

架构设计师应熟悉**业务领域知识**并熟练掌握**软件开发知识**，做到两者之间的平衡。

**八项专业素质（重点考点）**：

| 序号 | 素质类型 | 核心要点 |
|------|----------|----------|
| **1** | 掌握业务领域的知识 | 领域是从事于某一行业的人理解并归纳的一组概念和术语知识或活动范畴（UML, User guide 1999）；熟悉业务使得架构设计师能够预见可能发生的改变 |
| **2** | 掌握技术知识 | 不必是技术专家，但必须关注技术的重要因素；需要理解像Java EE或.NET这类平台上的可用关键框架；必须跟上技术的发展 |
| **3** | 掌握设计技能 | 设计过程是架构设计的核心内容；架构是关键设计决策的具体化；关键设计决策指关键结构设计决策、特定模型的选择和指导规格说明书等；设计能力是多年经验积累的结果 |
| **4** | 具备编程技能 | 开发人员是架构设计师必须打交道的最重要的团队成员；架构设计师应该具有一定的编程技能；优秀的架构设计师通常会编写一定量的代码 |
| **5** | 具备沟通能力 | **所有软技能中最重要的**；应具备有效的口头和书面表达能力；有效的沟通是项目成功的基础 |
| **6** | 具备决策能力 | 尤其在不很明确的情况下；不能果断决策会延误项目、失去信任；即使决策不总是正确，但必须学会纠正错误决策 |
| **7** | 知道组织策略 | 成功的架构设计师不仅仅关心技术；应对政治敏感并知道其在组织中的权利 |
| **8** | 应是谈判专家 | 在项目中尽可能早地把风险降到最低；消除风险的途径是通过精炼需求；能够清晰明白地表明各种折中方案的后果 |

### 1.2.3 架构设计师的知识结构

架构设计师综合的知识能力结构主要包括**10个方面**（选择题考点）：

**知识结构10项能力**：

7. **信息安全技术支持与管理保障能力**
8. **IT审计、治理与基本需求的分析和获取能力**
9. **面向软件系统可靠性与系统生命周期的质量保障服务能力**
10. **对新技术与新概念的理解、掌握和分析能力**

**架构设计师的综合素质要求**：
