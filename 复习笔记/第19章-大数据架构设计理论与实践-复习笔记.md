# 第19章 大数据架构设计理论与实践 — 复习笔记

## 章节概述

本章围绕大数据处理系统的核心问题展开，系统讲解了传统数据处理系统的局限性、大数据系统面临的技术挑战、大数据架构应具备的关键特征，以及两大主流架构（Lambda 和 Kappa）的原理、实现、优缺点与选型策略。案例分析部分展示了两种架构在实际项目中的应用。

---

## 一、传统数据处理系统存在的问题 ⭐

### 1.1 核心问题链

| 阶段 | 问题 | 应对手段 | 局限性 |
|------|------|----------|--------|
| 初期 | 用户量增加导致数据库过载 | Web 与 DB 间加异步队列缓冲 | 未从根本上解决过载 |
| 中期 | 队列处理跟不上 | 多工作处理层并发 | DB 再次成为瓶颈 |
| 后期 | 单机性能极限 | 数据库分区（Hash 分区） | 需应用端感知分区 |
| 再后期 | 分区不够用 | Resharding（重分区） | 耗时、数据迁移复杂、运维风险高 |
| 最终 | 整体架构复杂度爆炸 | 队列 + 分区 + 复制 + 重分区脚本 | 应用需了解 schema 和分区，DB 本身不感知分区 |

### 1.2 根本矛盾

- 数据库对分区**不感知**，无法帮助应对分区、复制与分布式查询
- 系统**未对人为错误进行工程设计**，仅靠备份不能治本
- 传统架构性能被压榨至极限，检索延迟和硬件故障频发
- 本质是**增量修补**（"挤牙膏"），需要新架构

## 二、大数据处理系统架构分析

### 2.1 三大挑战 ⭐

| 序号 | 挑战 | 核心要点 |
|------|------|----------|
| 1 | 处理非结构化和半结构化数据 | 结构化数据仅占 ~15%，85% 为非结构化；需"一次挖掘"（粗糙知识）→"二次挖掘"（智能知识） |
| 2 | 复杂性与不确定性刻画及系统建模 | 需建立结构化与非结构化数据之间的转换原则；管理科学/最优化理论发挥作用 |
| 3 | 数据异构性与决策异构性的关系 | 大数据改变了传统管理决策结构模式；需通过"二次挖掘"产生"智能知识"作为桥梁 |

**关键概念：**
- **一次挖掘**：从数据中提取"粗糙知识"（潜在模式）
- **二次挖掘**：将粗糙知识与主观知识（经验、常识、情境知识、用户偏好）结合，产生"智能知识"

### 2.2 大数据系统应具备的八大特征 ⭐⭐

> 由 Storm 之父 Nathan Marz 提出

| 特征 | 关键词 | 核心说明 |
|------|--------|----------|
| 1. 鲁棒性和容错性 | 人 > 机器 | **人为操作容错性比机器容错性更重要**；系统需从错误中快速恢复 |
| 2. 低延迟读取和更新 | 毫秒级 | 在保证鲁棒性前提下实现几毫秒到几百毫秒的延迟 |
| 3. 横向扩容 (Scalable) | Scale Out | 线性扩展，增加机器而非增强单机（Scale Out > Scale Up） |
| 4. 通用性 | 多领域 | 支持金融、社交、电商等多种应用场景 |
| 5. 延展性 | 可扩展 | 新功能可添加；具备大规模迁移能力 |
| 6. 即席查询 (Ad Hoc) | 灵活查询 | 用户可按需进行多样化数据查询 |
| 7. 最少维护 | 低复杂度 | 用机制简单的组件和算法降低底层复杂度 |
| 8. 可调试性 | 可追踪 | 每个值都可追踪其产生过程 |

## 三、Lambda 架构 ⭐⭐⭐

### 3.1 来源与定义

- **提出者**：Nathan Marz（Storm 作者）
- **定义**：用于**同时处理离线和实时数据**的、可容错的、可扩展的分布式系统架构
- **核心原则**：不可变性、读写分离、复杂性隔离
- **可集成组件**：Hadoop、Kafka、Spark、Storm 等

### 3.2 应用场景

| 场景 | 说明 |
|------|------|
| 机器学习 | 利用 Lambda 架构的**输出**，进行模式识别和算法训练 |
| 物联网 | 作为大数据系统的**输入**源，传感器产生海量实时数据流 |
| 流处理 | 速度层提供最新数据的低延迟实时视图；关注"最终精度"概念 |

> **最终精度 (Eventual Accuracy)**：批处理层关注精确计算，速度层关注近似计算，近似计算最终由下一组批处理视图取代。

### 3.3 三层架构（核心重点） ⭐⭐⭐

```
┌─────────────────────────────────────────────┐
│              服务层 (Serving Layer)           │
│    合并 Batch View + Real-time View → 最终结果 │
├──────────────────┬──────────────────────────┤
│  批处理层         │  加速层 (Speed Layer)     │
│  (Batch Layer)   │  处理增量实时数据流        │
│  存储主数据集     │  不断更新 Real-time View   │
│  预计算 Batch View│  增量算法，复杂度高        │
└──────────────────┴──────────────────────────┘
         ↑ 原始不可变数据集
```

#### (1) 批处理层 (Batch Layer)

- **两大功能**：存储数据集 + 生成 Batch View
- **主数据集三属性**：①原始 ②不可变 ③永远真实
- **核心概念 — Monoid 特性**：
  - 来源于范畴学，满足**结合律**
  - 满足 Monoid 特性 → 可分解到多台机器**并行运算**再合并
  - 不满足的可拆分（如平均值 → 分子分母分别求和）
- **View**：针对查询的预计算结果，是查询优化核心
- **典型实现**：HDFS 存储 + MapReduce/Spark 计算

#### (2) 加速层 (Speed Layer)

- 处理**最近的增量数据流**（非全体数据集）
- 接收新数据后**不断更新** Real-time View（增量计算）
- 与批处理层的关键区别：增量 vs 全量

**分离的优点：**
- **容错性**：Speed Layer 的数据也写入 Batch Layer，重新计算时可修正错误（最终一致性）
- **复杂性隔离**：高复杂度的增量算法隔离在 Speed Layer
- **可扩展性**：两层独立扩展

#### (3) 服务层 (Serving Layer)

- 响应查询请求，**合并** Batch View 和 Real-time View
- 合并方式：
  - 满足 Monoid → 直接合并
  - 不满足 → 拆分成满足 Monoid 的子函数分别合并
  - 也可依据业务规则合并

### 3.4 典型技术选型

| 层次 | 技术 |
|------|------|
| 批处理层（存储） | Hadoop (HDFS) |
| 加速层（计算） | Spark / Storm |
| 服务层（存储+查询） | HBase / Cassandra |
| 视图创建 | Hive |

### 3.5 优缺点

| 优点 | 缺点 |
|------|------|
| 容错性好（可重新计算视图） | 全场景覆盖带来编码开销 |
| 查询灵活度高（支持即席查询） | 针对具体场景重新离线训练益处不大 |
| 易伸缩（完全分布式） | 重新部署和迁移成本高 |
| 易扩展（添加 View 只需加函数） | **需维护两套代码/系统** |

### 3.6 与相关架构模式的关系

| 对比对象 | 关系 |
|----------|------|
| **事件溯源 (Event Sourcing)** | Lambda 的数据集存储与 Event Sourcing 思想一致，都使用统一数据模型对事件进行定义，可通过事件重算实现容错 |
| **CQRS（命令查询职责分离）** | Lambda 的写操作（批/流处理生成 View）与读操作（读取 View 直接得到结果）实现了读写分离 |

## 四、Kappa 架构 ⭐⭐⭐

### 4.1 来源与定义

- **提出者**：Jay Kreps（Apache Kafka / Apache Samza 作者）
- **定义**：只通过**流计算一条数据链路**计算并产生视图的架构
- **核心思想**：在 Lambda 基础上优化，**删除 Batch Layer**，用消息队列替代数据通道

### 4.2 数据系统本质理解

$$\text{数据系统} = \text{数据} + \text{查询}$$

**数据的两个关键性质：**

| 性质 | 含义 | 重要性 |
|------|------|--------|
| **When（时间相关）** | 数据在某个时间点产生，具有全局先后顺序 | 决定分布式系统中数据的全局次序和最终结果 |
| **What（不可变）** | 数据本身不可变，过往数据是事实 | 操作只有读取和追加（CRUD → CR），Update/Delete 本质是新数据 |

**不可变存储的好处：**
- **简单**：只需追加，无需索引和更新
- **应对错误**：所有数据都在，可丢弃错误数据并重新计算（Re-computation）

### 4.3 体系结构

```
源数据 → 实时数据处理引擎 (Flink) → 服务后端 → 业务查询
                ↕
         存储介质（数据湖：历史数据 + 结果数据）
```

- 输入数据直接由实时处理引擎处理
- 中间结果存储在存储介质中
- 需要重新处理时，从数据湖经消息队列**重播**

### 4.4 重新处理历史数据的方法

1. 部署 Kafka，设置日志保留期（Retention Period）
2. 启动新的 Kafka 作业实例，将 Log Offset 设为 0，从头重算
3. 新视图赶上旧视图时，切换应用读取新视图
4. 停止旧作业实例，删除旧视图

### 4.5 优缺点

| 优点 | 缺点 |
|------|------|
| 实时和离线代码统一，方便维护 | 消息中间件缓存数据量和回溯有**性能瓶颈** |
| 统一数据口径，避免合并问题 | 大量实时流关联时依赖计算系统能力，可能**数据丢失** |
| 查询历史数据只需重放 | 抛弃离线处理模块的同时**抛弃了其稳定可靠的特点** |

### 4.6 Kappa 变形架构 ⭐

#### (1) Kappa+ 架构（Uber 提出）

- **核心思想**：流计算框架直接读 HDFS 数据仓库数据，无需为 backfill 长期保存日志
- **任务分类**：
  - **无状态任务**：根据吞吐速度合理并发扫描全量数据
  - **时间窗口任务**：按时间粒度分区存储，按时间顺序依次计算 partition
- **关键框架**：Apache Hudi（支持更新/删除 parquet 数据 + 增量消费）

#### (2) 混合分析系统的 Kappa 架构

- 在 Kappa 基础上增加数据分析流程
- 典型方案：Kafka + Flink + ElasticSearch（弥补分析能力不足）
- 属于 Kappa 和 Lambda 之间的**折中方案**

## 五、Lambda vs Kappa 对比与选型 ⭐⭐⭐

### 5.1 多维度对比表（高频考点）

| 对比维度 | Lambda 架构 | Kappa 架构 |
|----------|-------------|------------|
| **复杂度与维护成本** | 两套系统/代码，复杂度高，成本高 | 一套系统/代码，复杂度低，成本低 |
| **计算开销** | 批处理 + 实时计算持续运行，开销大 | 必要时才全量计算，开销相对小 |
| **实时性** | 满足（View 合并策略） | 满足（流式计算直接处理） |
| **历史数据处理** | 批式全量处理，吞吐大，**能力强** | 流式全量处理，吞吐较低，**能力较弱** |
| **架构层数** | 三层（批处理 + 加速 + 服务） | 两层（实时 + 服务） |
| **代码维护** | 两套代码需保持一致 | 一套代码 |

### 5.2 选型决策因素

| 考虑因素 | 选 Lambda | 选 Kappa |
|----------|-----------|----------|
| **业务需求** | 依赖 Hadoop/Spark/Storm | 偏好流式计算 + Flink |
| **算法复杂度** | 离线/实时结果不能统一（如 ML 训练+验证） | 算法模型支持同时执行批/流 |
| **开发维护成本** | 有足够经济、技术、人力资源 | 不希望过多投入 |
| **历史数据量** | 频繁接触海量数据集分析 | 始终使用小规模数据集 |
| **参数调整频率** | 不频繁 | 频繁修改算法模型参数 |

## 六、案例分析要点 ⭐⭐

### 6.1 Lambda 架构案例

| 案例 | 架构层次 | 核心技术 | 关键经验 |
|------|----------|----------|----------|
| **某网奥运** | 数据集成层 + 存储层 + 计算层 + 应用层 | Nginx+Flume→Kafka, HBase, Spark Streaming, MemSQL | 实时计算用增量计算（非重算），离线用不可变存储追加 |
| **某网广告平台** | 典型 Lambda 三版演进 | Kafka→HDFS→Hive→MySQL, Spark Streaming→Redis | V1 服务层瓶颈 → V2 减少服务层计算 → V3 只维护一张 MySQL 表 |

**广告平台演进核心教训：**
- 标准 Lambda 架构在数据来源多时，服务层成为性能瓶颈
- 改进方向：**把服务层的工作提前到数据收集/计算层处理**

### 6.2 Kappa 架构案例

| 案例 | 核心技术栈 | 关键设计 |
|------|------------|----------|
| **某证券实时日志分析** | Filebeat→Kafka→Flink→ElasticSearch+OpenTSDB | 统一 Flink 处理全部数据；自主研发可配置化计算框架 |
| **某电商智能决策** | Kafka→Flink→Hive+Tair；Zookeeper 通知机制 | 实时流数据直接用于决策参数计算，提升模型准确性 |

## 七、易混淆概念辨析

| 概念对 | 区别 |
|--------|------|
| **Batch View vs Real-time View** | Batch View 基于全体数据集预计算，精确；Real-time View 基于增量数据流实时更新，近似 |
| **Monoid 特性 vs 结合律** | Monoid 是范畴学概念，其重要特性之一是满足结合律；结合律使分布式并行计算成为可能 |
| **Scale Out vs Scale Up** | Scale Out = 增加机器数量（横向扩展）；Scale Up = 增强单机性能（纵向扩展）；大数据架构偏好 Scale Out |
| **最终精度 vs 最终一致性** | 最终精度是 Lambda 的概念（速度层近似→批处理层精确替代）；最终一致性是 CAP 理论概念（Speed Layer 错误在 Batch 重算时修正） |
| **Event Sourcing vs CQRS** | Event Sourcing 关注事件驱动的**数据持久化**方式；CQRS 关注**读写操作分离**；Lambda 同时借鉴了两者 |
| **Kappa vs Kappa+** | Kappa 用消息队列存储所有数据（成本高）；Kappa+（Uber）直接读 HDFS 数据仓库（Apache Hudi 框架） |

## 八、高频考点速记

1. ⭐ Lambda 三层：批处理层（Batch）、加速层（Speed）、服务层（Serving）
2. ⭐ 主数据集三属性：原始、不可变、永远真实
3. ⭐ Monoid 特性 = 结合律 → 分布式并行运算
4. ⭐ Kappa = Lambda 去掉 Batch Layer，只保留流计算一条链路
5. ⭐ 数据两大性质：When（时间相关）+ What（不可变）
6. ⭐ 大数据八大特征（Nathan Marz 提出）
7. ⭐ Lambda vs Kappa 四维对比：复杂度、计算开销、实时性、历史数据处理
8. ⭐ Lambda 缺点：两套代码/系统维护成本高
9. ⭐ Kappa 缺点：消息队列缓存数据回溯有性能瓶颈
10. ⭐ Kappa+ 由 Uber 提出，核心是用 HDFS + Apache Hudi 替代消息队列长期存储
