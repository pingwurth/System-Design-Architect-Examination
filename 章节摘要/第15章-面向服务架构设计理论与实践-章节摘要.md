## 一、SOA 概述

### 1.1 SOA 定义 ⭐

**两种标准定义：**

| 视角 | 定义要点 |
|------|----------|
| **应用视角** | 一种应用框架，将业务划分为单独的业务功能和流程（服务），无需依赖应用程序及其运行平台，提高业务灵活性 |
| **软件原理视角** | 一个**组件模型**，将应用程序的不同功能单元（服务）通过**定义良好的接口和契约**联系起来，接口采用**中立方式**定义，独立于硬件平台、操作系统和编程语言 |

> 考试关键：SOA 的核心是**松耦合**、**标准化接口**、**服务复用**。

### 1.2 业务流程与 BPEL ⭐

- **BPEL**（Business Process Execution Language for Web Services）：面向 Web 服务的**业务流程执行语言**
- 用 BPEL 可以**组合、编排和协调** Web 服务，自上而下实现 SOA
- 将多个 Web 服务组合成一个新的复合服务（业务流程）
- BPEL 本质：将现有 Web Services 按照业务流程整理成一个新的 Web Service

### 1.3 SOA 发展三阶段

| 阶段 | 时间 | 标志 | 关键标准 |
|------|------|------|----------|
| **萌芽阶段** | 20世纪90年代末~21世纪初 | XML 技术 | XML、XSD、XSLT |
| **标准化阶段** | 2000年以后 | Web 服务概念提出 | **SOAP、WSDL、UDDI**（Web服务三剑客） |
| **成熟应用阶段** | 2005年开始 | 厂商协作组织 | **SCA、SDO、WS-Policy** |

### 1.4 SOA 与微服务对比 ⭐⭐⭐（高频考点）

| 对比维度 | SOA | 微服务 |
|----------|-----|--------|
| **服务粒度** | 粗粒度 | 细粒度 |
| **存在形式** | 功能模块 | 独立进程 |
| **接口方式** | 多为 SOAP/WSDL | **HTTP RESTful**（更通用） |
| **通信方式** | 远程通信（经 ESB） | REST/消息队列 |
| **部署方式** | 集中式（ESB 链接各子系统） | **分布式、去中心化** |
| **ESB** | 依赖 ESB | **去除 ESB** |
| **数据库** | 可能共享 | **每个服务独立数据库** |
| **耦合度** | 松耦合 | 更松耦合 |
| **响应速度** | 较慢（ESB 中介） | 较快 |

## 二、SOA 参考架构（IBM WebSphere）

IBM 业务集成参考架构按"关注点分离"划分 6 大类服务：

| 服务类型 | 核心职责 | 典型组成 |
|----------|----------|----------|
| ⭐**连接服务（ESB）** | 服务间连接性 | 服务注册、消息路由、协议转换、数据转换 |
| **业务逻辑服务** | 实现业务逻辑 | 业务应用服务、伙伴服务、应用/信息资产 |
| **控制服务** | 人/流程/信息集成 | 信息服务、流程服务、交互服务 |
| **业务创新和优化** | 监控业务性能 | 公共事件框架、采集服务、监控服务（BPM/KPI） |
| **开发服务** | 全生命周期支持 | 建模/设计/实现/测试服务 |
| **IT 服务管理** | 基础设施管理 | 安全/目录服务、系统管理/虚拟化 |

### ESB（企业服务总线）核心要点 ⭐⭐⭐

- ESB 是一种**架构模式**，不等于特定产品
- 基于**总线模式**简化集成拓扑
- 核心能力：
  1. 位置透明的消息路由和寻址
  2. 服务注册和命名管理
  3. 多种消息传递范型（请求/响应、发布/订阅）
  4. 多种传输协议支持
  5. 多种数据格式及其转换
  6. 日志和监控

## 三、SOA 主要协议和规范 ⭐⭐⭐

### 3.1 Web 服务三大基础协议

| 协议 | 全称 | 作用 | 关键特征 |
|------|------|------|----------|
| **UDDI** | 统一描述、发现和集成协议 | 服务**发现**——商业实体彼此发现、共享信息 | 全局注册体系架构，目录列表角色 |
| **WSDL** | Web 服务描述语言 | 服务**描述**——描述服务接口 | XML 语言，描述服务做什么、如何访问、位于何处 |
| **SOAP** | 简单对象访问协议 | 服务**通信**——分布式环境交换信息 | 基于 XML，包含封装/编码规则/RPC 表示/绑定 |

### 3.2 WSDL 文档结构 ⭐

按从内到外顺序：

```
types（数据类型定义）
  ↓
message（消息数据结构）
  ↓
operation（操作抽象描述）
  ↓
portType（访问入口点类型的操作集合）
  ↓
binding（协议和数据格式绑定）
  ↓
port（单个服务访问点 = 绑定 + 地址）
  ↓
service（端口集合）
```

### 3.3 SOAP 四部分

1. **SOAP 封装（Envelope）**：描述消息内容、发送者、接收者和处理方式
2. **SOAP 编码规则（Encoding Rules）**：表示数据类型的实例
3. **SOAP RPC 表示**：远程过程调用和应答的协定
4. **SOAP 绑定（Binding）**：使用底层协议交换信息

> SOAP 设计目标：**简单性**和**可扩展性**

### 3.4 REST 规范 ⭐⭐

**REST**（Representational State Transfer，表述性状态转移）——一种**架构风格**而非协议。

| 核心概念 | 说明 |
|----------|------|
| **资源（Resource）** | REST 以资源为中心，用 **URI** 标识资源 |
| **表述（Representational）** | 描述资源在某一时间的状态，常用 JSON/XML/HTML |
| **状态转移（State Transfer）** | 应用状态由客户端维护，资源状态由服务端维护，通过 HTTP 方法实现 |
| **超链接** | 资源表述中包含相关资源 URI，便于客户端请求 |

**REST vs SOAP 对比：**

| 维度 | REST | SOAP |
|------|------|------|
| 本质 | 架构风格 | 协议 |
| 数据格式 | JSON/XML/HTML/文本 | XML |
| 接口风格 | HTTP 方法（GET/POST/PUT/DELETE） | RPC 式 |
| 复杂度 | 轻量 | 较重 |
| 适用场景 | 互联网/Web API | 企业内部/安全性要求高 |

## 四、SOA 设计原则 ⭐⭐

| 设计原则 | 要点 |
|----------|------|
| **无状态** | 服务不依赖前一个请求的状态，避免请求者依赖提供者状态 |
| **单一实例** | 避免功能冗余 |
| **明确定义的接口** | WSDL 定义接口，WS-Policy 描述规约，XML Schema 定义消息格式；接口一旦公布**不能随意更改** |
| **自包含和模块化** | 服务封装业务上稳定、重复出现的活动，独立部署/版本控制/管理/恢复 |
| **粗粒度** | 服务数量不宜太大，消息交互而非 RPC，交互频度低但消息量大 |
| **松耦合** | 使用者只看到接口，位置/实现/状态不可见 |
| **重用能力** | 服务应该可以重用 |
| **互操作性/兼容/策略声明** | WS-Policy 定义可配置的互操作语义 |

## 五、SOA 设计模式 ⭐⭐

### 5.1 服务注册表模式

- 在设计时段使用，也具有运行时段功能
- 支持服务合同、策略和元数据的开发/发布/管理
- 提供**策略执行点（PEP）**
- 三大治理功能：**服务注册、服务位置、服务绑定**
- UDDI 是主要注册环境之一

### 5.2 企业服务总线（ESB）模式

- 以**中间件**形式支持服务单元交互的软件平台
- 由消息中间件发展而来
- 事件驱动的消息交互模式
- 实现组件的**位置透明**和**协议透明**
- 最大限度解耦组件间依赖

### 5.3 微服务模式

**微服务架构核心优势：**
1. **复杂应用解耦**——按业务逻辑拆分，每个服务专注单一功能
2. **独立**——独立开发/测试/部署，变更不影响全局
3. **技术选型灵活**——去中心化，各服务可选不同技术栈
4. **容错**——故障隔离在单个服务，不会全局瘫痪
5. **松耦合，易扩展**——每个服务可独立扩展

**常见微服务设计模式：**

| 模式 | 说明 |
|------|------|
| **聚合器微服务** | 调用多个微服务组合功能，有独立缓存和数据库 |
| **代理微服务** | 仅委派请求和数据转换，不聚合数据 |
| **链式微服务** | 同步链式调用（A→B→C），链不宜过长 |
| **分支微服务** | 聚合器模式扩展，同时调用两个独立微服务链 |
| **数据共享微服务** | 多微服务共享缓存和数据库（过渡阶段使用） |
| **异步消息传递微服务** | 用消息队列替代 REST 同步调用（Kafka/RabbitMQ 等） |

**微服务面临的挑战：**
- 分布式复杂性（服务发现、链路跟踪困难）
- 分区数据库（CAP 约束，追求最终一致性）
- 测试复杂性（需启动所有依赖服务）
- 部署管理难度（监控/管理/分发/扩容）

## 六、构建 SOA 架构注意事项 ⭐

### 6.1 原有系统集成需求

- **优先考虑重用已有投资**，而非替换遗留系统
- 集成类型包括：应用程序集成、终端用户界面集成、流程集成、信息集成
- 集成功能应由**服务提供**，而非特定应用程序

### 6.2 服务粒度控制 ⭐⭐

| 粒度 | 适用场景 | 特点 |
|------|----------|------|
| **粗粒度** | 暴露给系统**外部** | 保证一致的调用方式，可用 BPEL 组合细粒度操作 |
| **细粒度** | 企业系统架构**内部** | 提供灵活性，但交互模式易变 |

### 6.3 无状态服务设计 ⭐

- 服务应是**独立的、自包含的请求**，不依赖前一个请求的状态
- 需要状态时定义为 BPEL 业务流程
- 推荐使用**无状态 Session Bean** 实现
- 无状态 Session Bean 优势：
  - EJB 容器自动支持并发（串行化请求）
  - 自动提供安全和事务支持
  - 支持群集和 Bean 池，提高可伸缩性

## 七、SOA 实施过程 ⭐

### 7.1 选择 SOA 解决方案

三个方面：
1. 选择能进行**全局规划**的方案
2. 充分考虑**企业自身需求**
3. 从**平台、实施方法与途径、供应商**三方面考察

### 7.2 业务流程分析

#### 建立服务模型（三种方法）

| 方法 | 别名 | 思路 |
|------|------|------|
| **自顶向下分解法** | 领域分解 | 从业务流程逐层分解至业务活动，通过业务组件模型划分 |
| **业务目标分析法** | 目标服务建模 | 从业务目标出发→子目标→分配给服务实现，形成"目标服务树" |
| **自底向上分析法** | 遗留资产分析 | 从已有系统功能模块发现可重用的服务 |

#### 建立业务对象

| 类型 | 说明 | 示例 |
|------|------|------|
| **实体业务对象** | 表达人/地点/事物/概念（名词） | 客户、订单、物品 |
| **过程业务对象** | 表达业务处理过程（动词） | 依赖于实体业务对象 |
| **事件业务对象** | 表达系统操作产生的事件 | — |

#### 服务接口设计原则

- 服务接口应包含**多个语义相关的操作**
- **无状态接口**是最佳选择
- 请求消息应包含完成操作的**全部必要信息**

## 九、易混淆概念对比

| 对比项 | 区别要点 |
|--------|----------|
| SOA vs 微服务 | SOA 集中式（ESB）、粗粒度；微服务去中心化、细粒度、独立进程 |
| UDDI vs WSDL vs SOAP | UDDI=发现/注册、WSDL=描述接口、SOAP=通信协议 |
| REST vs SOAP | REST 是架构风格（轻量）；SOAP 是协议（重量级） |
| ESB vs 点对点 | ESB 总线模式（解耦）；点对点（N 个应用需 N(N-1)/2 个连接） |
| BPEL vs WSDL | BPEL 编排业务流程；WSDL 描述服务接口 |
| 粗粒度 vs 细粒度接口 | 粗粒度用于外部集成；细粒度用于内部实现 |
| SCA/SDO vs WS-* | SCA/SDO 是编程模型基础；WS-* 是通信/安全/事务协议族 |

## 十、核心公式/模型速记

```
SOA 解决问题：打破"信息孤岛"
  步骤：(1) 把应用和资源转换成服务 → (2) 标准化服务，形成资源共享

EAI 问题：N 个应用互通需要 N(N-1)/2 个 EAI Server（几何级增长）
SOA 解决：通过 ESB 总线模式，N 个应用只需 N 个连接

服务设计公式：
  粗粒度服务 = BPEL 组合细粒度操作
  无状态服务 = 独立请求 + 无上下文依赖
```
