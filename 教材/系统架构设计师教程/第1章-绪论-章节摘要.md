## 二、核心知识点

### 1.1 系统架构概述

#### 1.1.1 系统架构的定义及发展历程 ⭐

**架构定义（IEEE 1471-2000）**：

> 架构是体现在**组件**中的一个系统的基本组织、它们**彼此的关系**与**环境的关系**及指导它的设计和发展的**原则**。

关键术语：
- **系统**：组织起来完成特定功能的组件集
- **环境/上下文**：决定系统开发、运作、政策及影响的环境和设置
- **任务**：由利益相关者通过系统达到目标的系统用途或操作

**架构设计的作用**（5点）：
1. 解决相对复杂的需求分析问题
2. 解决非功能属性在系统占据重要位置的设计问题
3. 解决生命周期长、扩展性需求高的系统整体结构问题
4. 解决系统基于组件需要的集成问题
5. 解决业务流程再造难的问题

**发展历程四阶段**：

| 阶段 | 时间 | 核心事件/成果 |
|---|---|---|
| 基础研究阶段 | 1968—1994 | NATO会议提出软件工程概念；模块化开发方法；SOA思想；MIS分层架构雏形 |
| 概念体系和核心技术形成阶段 | 1999—2000 | IEEE 1471-2000标准发布（标志性事件）；软件组件化技术；Perry & Wolf: {elements, forms, rationale} |
| 理论体系完善与发展阶段 | 1996至今 | 架构描述语言（C2SADL、Wright、ACME等）；架构分析方法（SAAM、ATAM、CBAM）；架构风格五大类 |
| 普及应用阶段 | 2000至今 | 第一届IFIP软件架构会议（1999）；ADML（基于XML）；软件产品线架构 |

#### 模块化开发 ⭐

模块化分解规则（6条）：
1. **最高模块内聚** — 一个模块只实现一种功能
2. **最低耦合** — 不同模块间关系尽可能弱
3. **模块大小适度** — 颗粒过大维护困难，过小耦合增加
4. **模块调用链深度不可过多**
5. **接口简单精炼** — 扇入扇出数不宜太大，具有信息隐蔽能力
6. **尽可能复用已有模块**

#### 组件化 vs 模块化 vs 应用集成 ⭐

| 概念 | 含义 | 特点 |
|---|---|---|
| **模块化** | 逻辑上切分 | 物理上（代码）通常没有真正隔离 |
| **组件化** | 比模块化更独立 | 具有可组装性和可插拔性；组件间无直接耦合；通过组装后交互 |
| **应用集成** | 将不同平台应用集成到单一系统 | 比组件化结合更紧密 |

#### 软件架构五大风格（David Garland & Mary Shaw）⭐⭐

| 风格 | 说明 |
|---|---|
| **数据流风格** | 数据沿管道流动处理（如管道-过滤器） |
| **调用/返回风格** | 主程序/子程序调用（如C/S、分层架构） |
| **独立组件风格** | 组件独立运行，通过事件/消息通信 |
| **虚拟机风格** | 提供虚拟执行环境（如解释器、规则系统） |
| **仓库风格** | 以共享数据为中心（如数据库、黑板） |

#### 架构分析方法 ⭐

| 方法 | 全称 |
|---|---|
| **SAAM** | 软件架构分析方法 |
| **ATAM** | 架构权衡分析法 |
| **CBAM** | 成本效益分析法 |
| **SBAR** | 基于场景的架构再工程 |
| **ALPSM** | 架构层次的软件可维护性预测 |
| **SAEM** | 软件架构评估模型 |

#### 1.1.2 软件架构的常用分类及建模方法 ⭐⭐

**五种典型架构模型**：

| 架构 | 核心特征 | 关键组成 |
|---|---|---|
| **分层架构** | 最常用，水平分层，层间接口通信 | 表现层→业务层→持久层→数据库（四层结构） |
| **事件驱动架构** | 通过事件通信 | 事件队列→分发器→事件通道→事件处理器 |
| **微核架构（插件架构）** | 内核最小化，功能通过插件实现 | 内核(Core) + 插件(Plugins) |
| **微服务架构** | SOA的升级，分布式独立部署单元 | RESTful API模式 / RESTful应用模式 / 集中消息模式 |
| **云架构** | 解决扩展性和并发，最易扩展 | 处理单元(Processing Unit) + 虚拟中间件(Virtualized Middleware) |

**云架构的虚拟中间件四个组件**：
- 消息中间件 (Messaging Grid) — 管理请求和会话控制
- 数据中间件 (Data Grid) — 数据复制/同步
- 处理中间件 (Processing Grid) — 可选，协调不同处理单元
- 部署中间件 (Deployment Manager) — 处理单元启停和负载监控

**四种架构建模方法**：

| 模型 | 侧重点 |
|---|---|
| **结构模型** | 以构件、连接件刻画结构，核心是架构描述语言 |
| **框架模型** | 更侧重整体的结构，针对特殊问题 |
| **动态模型** | 研究系统"大颗粒"行为（重新配置或演化） |
| **过程模型** | 研究构造系统的步骤和过程 |

**"4+1"视角模型（Philippe Kruchten, 1995）** ⭐⭐：

| 视角 | 关注点 |
|---|---|
| **逻辑视角** (Logical) | 功能需求，系统做什么 |
| **过程视角** (Process) | 并发、同步、通信 |
| **物理视角** (Physical) | 系统部署、分布 |
| **开发视角** (Development) | 软件模块组织 |
| **场景视角** (Scenarios) | 验证和集成 |

#### 1.1.3 软件架构的应用场景

- 现代大型软件很少使用单一架构风格，而是**混合多种风格**
- 不同架构风格从不同视角描述系统，保证可靠性、可扩展性、可维护性等非功能属性

### 1.2 系统架构设计师概述

#### 架构师的分类 ⭐⭐

**从组织上划分，架构师通常可分为5大类**：

| 类型 | 英文名称 |
|---|---|
| **业务架构师** | Business Architect |
| **主题领域架构师** | Domain Architect |
| **技术架构师** | Technology Architect |
| **项目架构师** | Project Architect |
| **系统架构师** | System Architecture |

**微软公司对架构设计师的分类（4种）**：

根据架构师关注的领域不同，可将系统架构设计师分为4种

| 类型 | 英文缩写 |
|---|---|
| **企业架构师** | EA (Enterprise Architect) |
| **基础结构架构师** | IA (Infrastructure Architect) |
| **特定技术架构师** | TSA (Technology Architect) |
| **解决方案架构师** | SA (Solution Architect) |

> **注意区分**：解决方案架构师属于微软公司的分类方法，不属于组织划分的5大类。

#### 1.2.1 架构设计师的定义、职责和任务 ⭐

**定义**：架构设计师是负责系统架构的人、团队或组织（IEEE 1471-2000）。是系统或产品线的设计责任人。

**核心职责**：**技术领导**
- 拥有进行技术决策的权威
- 项目经理关注管理资源、进度和成本；架构师关注技术决策
- 两者代表项目的公共角色

**三大技术任务**：
1. **抽象设计**
2. **非功能设计**
3. **关键技术设计**

**架构师角色可由团队履行**，但需要**首席架构设计师**作为单点协调人。

#### 1.2.2 架构设计师应具备的专业素质 ⭐

| 素质 | 要点 |
|---|---|
| 掌握业务领域知识 | 理解业务模型，预见可能的改变 |
| 掌握技术知识 | 关注技术的重要因素而非细节，跟上技术发展 |
| 掌握设计技能 | 多年经验积累，关键结构设计决策 |
| 具备编程技能 | 参与代码实现，获得第一手反馈 |
| 具备沟通能力 | 最重要的软技能，传达系统愿望，激励团队 |
| 具备决策能力 | 在不明确情况下果断决策，学会纠正错误决策 |
| 知道组织策略 | 对政治敏感，确保项目获得支持 |
| 应是谈判专家 | 尽早降低风险，清晰表明折中方案的后果 |

#### 1.2.3 架构设计师的知识结构

10方面知识能力：
1. 战略规划能力
2. 业务流程建模能力
3. 信息数据架构能力
4. 技术架构设计和实现能力
5. 应用系统架构的解决和实现能力
6. 基础IT知识及基础设施、资源调配能力
7. 信息安全技术支持与管理保障能力
8. IT审计、治理与基本需求分析和获取能力
9. 面向软件系统可靠性与系统生命周期的质量保障服务能力
10. 对新技术与新概念的理解、掌握和分析能力

### 1.3 如何成为一名好的系统架构设计师

#### 1.3.1 优秀架构师的6种角色特质（Pat Kua）⭐

| 角色 | 核心要点 |
|---|---|
| **作为领导者** | 像导师，带领团队向技术愿景前进；借助讲故事、影响力、引导冲突 |
| **作为开发人员** | 避免"象牙塔式架构师"，多与开发人员在一起，了解系统约束 |
| **聚焦系统** | 不仅关注代码，还要满足部署、测试、性能、安全、可支持性等质量属性 |
| **具备企业家思维** | 从成本和收益两角度考虑技术选型，通过架构调研收集信息 |
| **权衡策略与战术思维** | 在敏捷度和一致性之间平衡；建立技术雷达 |
| **良好的沟通** | 使用听众熟悉的术语，图表和书面记录（架构决策日志） |

#### 1.3.2 从工程师到架构师的成长路径 ⭐

| 阶段 | 年限 | 典型特征 | 核心积累 |
|---|---|---|---|
| **工程师** | 1~3年 | 在别人指导下完成开发 | 基础技能（语言、数据结构、开发环境） |
| **高级工程师** | 3~5年 | 独立完成开发 | 方案设计经验；深度(Why) + 理论(设计模式、SOLID等) |
| **技术专家** | 4~8年 | 某个领域的专家 | 拓展技术宽度；修改、扩展和优化架构 |
| **初级架构师** | 5~8年 | 独立完成一个系统的架构设计 | 形成自己的**架构设计方法论** |
| **中级架构师** | 8~10年+ | 完成复杂系统的架构设计 | 技术深度和技术理论的积累 |
| **高级架构师** | 10年+ | **创造新的架构模式** | 创造性（如MapReduce、Docker容器化） |

**工程师 vs 架构师的本质区别**：
- 工程师：追求完美，精准精确，关注程序本身
- 架构师：习惯不完美和一定条件下的不精确，核心工作是**权衡**

**成为架构师的三个关键能力**：
1. **判断力** — 准确判断系统复杂度在哪里，看出脆弱点
2. **执行力** — 使用合适方案解决复杂度问题
3. **创新力** — 创造新的解决方案解决复杂度问题

## 三、易混淆点对比

| 对比项 | 区别 |
|---|---|
| 模块化 vs 组件化 | 模块化是逻辑切分，组件化是物理隔离+可组装+可插拔 |
| 组件化 vs 应用集成 | 组件化比模块化更独立，但比应用集成结合更紧密 |
| SOA vs 微服务 | 微服务是SOA的升级，每个服务是独立部署单元 |
| 技术专家 vs 初级架构师 | 技术专家基于经验设计；架构师基于方法论指导设计 |
| 架构师 vs 项目经理 | 架构师关注技术决策；项目经理关注资源、进度和成本 |
