# 第9章 软件可靠性基础知识 - 考前复习笔记

## 章节概述

本章围绕软件可靠性的**概念、建模、管理、设计、测试、评价**六大主题展开。核心逻辑链：先定义可靠性是什么 → 如何定量描述 → 如何建模预测 → 如何在设计阶段保障 → 如何测试验证 → 如何评价结果。考试重点集中在**定量指标公式、可靠性设计技术（容错/检错）、可靠性模型分类**三个方向。

---

## 9.1 软件可靠性基本概念 ⭐

### 9.1.1 软件可靠性定义

**核心定义（IEEE 1983 / GB/T-11457）：** 在规定的条件下，在规定的时间内，软件不引起系统失效的概率。

定义四要素：

| 要素 | 含义 |
|------|------|
| 规定的时间 | 运行时间（工作+挂起的累计时间），属随机变量 |
| 规定的条件 | 运行环境（硬件、OS、DBMS、中间件、输入范围等） |
| 所要求的功能 | 必须完成的任务，不同任务可靠性不同 |
| 缺陷与失效 | 内在缺陷（固有）→ 外在失效（随机） |

**软件 vs 硬件可靠性差异（高频考点）：**

| 差异点 | 软件 | 硬件 |
|--------|------|------|
| 复杂性 | 高度复杂，设计错误是失效主因 | 相对简单 |
| 物理退化 | **不存在**物理退化 | 主要因物理退化失效 |
| 唯一性 | 软件唯一，复制不改变 | 任何两个硬件不可能完全相同 |
| 版本更新 | 快，需求变更/缺陷修复 | 慢，定型后一般不更改 |

> **考点提示：** 软件的唯一性决定了概率方法在硬件可靠性领域成功但在软件领域不理想。一个**正确**的软件任何时刻均可靠，但正确的硬件元器件可能在某时刻失效。

### 9.1.2 可靠性定量描述 ⭐⭐

**三种时间概念：**

| 时间类型 | 含义 | 精度 |
|----------|------|------|
| 自然时间（日历时间） | 年/月/日 | 最粗 |
| 运行时间 | 启动到结束的时段 | 中等 |
| **执行时间** | CPU实际执行指令的时间总和 | **最准确** ⭐ |

**核心指标（必记）：**

1. **失效概率 F(t)：** 到t时刻出现失效的概率
   - F(0) = 0；F(t) 单调递增；F(+∞) = 1

2. **可靠度 R(t)：** 不发生失效的概率
   - R(t) = 1 - F(t)
   - R(0) = 1；R(+∞) = 0

3. **失效强度 f(t)：** 单位时间出现失效的概率
   - f(t) = F'(t)（F(t)的导数）

4. **MTTF（平均失效前时间）：** 系统运行到故障发生的持续运行时间期望值
   - MTTF = ∫R(t)dt （从0到∞）

5. **MTTR（平均恢复前时间）：** 从故障到修复成功的时间，越短越好

6. **MTBF（平均故障间隔时间）：** ⭐
   - **MTBF = MTTF + MTTR**
   - 对指数分布系统，任一时刻到达故障的期望时间相等

**运行剖面（Operational Profile）：** 对系统使用条件的定义，输入值按时间分布或出现概率分布来定义。

### 9.1.3 可靠性目标

**失效严重程度类（Failure Severity Class）：** 对用户具有相同程度影响的失效集合。

两种划分标准：
- **按成本影响**：用数量级划分（如 >100万 / 10~100万 / 1~10万 / 0.1~1万 / <0.1万）
- **按系统能力影响**：系统崩溃/出错停止/重要操作无响应/部分操作无响应

**可靠性目标三要素：** 可靠度、故障强度、MTTF，需与交付时间和成本平衡。

### 9.1.4 可靠性测试的意义

五个要点（简记）：
1. 软件失效可能造成**灾难性后果**
2. 软件失效占计算机系统失效的**80%**
3. 软件可靠性技术比硬件**不成熟**
4. 软件费用**有增无减**，可靠性问题是主因之一
5. 系统对软件**依赖性越来越强**

### 9.1.5 广义 vs 狭义可靠性测试 ⭐

| 维度 | 广义可靠性测试 | 狭义可靠性测试（可靠性试验） |
|------|--------------|--------------------------|
| 定义 | 运用建模、统计、试验、分析等手段**最终评价**可靠性 | 按预定用例在预期环境中**获取可靠性数据** |
| 范围 | 完整的可靠性测试过程 | 面向缺陷的测试 |
| 目的 | 最终评价 | 用户使用的预演，数据用于可靠性评价 |

**可靠性测试三个目的：**
1. 发现各方面的**缺陷**
2. 为使用和维护提供**可靠性数据**
3. 确认是否达到**定量要求**

## 9.2 软件可靠性建模 ⭐

### 9.2.1 影响软件可靠性的因素

**三大因素（缺陷生命周期）：**
- **引入：** 产品特性 + 开发过程特性（技术、工具、人员、需求变化）
- **发现：** 用户操作方式 + 运行环境（运行剖面）
- **清除：** 失效发现 + 修复活动 + 可靠性投入

**五大技术因素：**

| 因素 | 说明 |
|------|------|
| 运行剖面（环境） | 同一软件在不同运行剖面下可靠性不同 |
| 软件规模 | 代码行数越多，缺陷可能性越大 |
| 软件内部结构 | 结构越复杂，缺陷可能越多 |
| 开发方法和环境 | 结构化方法明显优于非结构方法 |
| 可靠性投入 | 早期重视可靠性效果显著 |

### 9.2.2 建模方法

**模型组成四部分：**
1. **模型假设** - 实际情况的简化/规范化
2. **性能度量** - 输出量（失效强度、残留缺陷数等）
3. **参数估计方法** - 通过统计/预测确定参数
4. **数据要求** - 输入数据（可靠性数据）

**三大基本假设（核心考点）：**

| 假设 | 含义 |
|------|------|
| **代表性假设** | 测试用例代表实际运行剖面 |
| **独立性假设** | 失效独立发生于不同时刻 |
| **相同性假设** | 所有失效后果（等级）相同，只考虑发生时刻 |

**好模型的五个特性：**
1. 基于可靠的假设
2. 简单
3. 计算有用的量
4. 给出未来失效行为好的映射
5. 可广泛应用

**参数确定方式：**
- **估计：** 收集失效数据 → 统计分析 → 归纳参数
- **预测：** 用软件属性和开发过程 → 执行前确定参数

### 9.2.3 可靠性模型分类 ⭐

**十大模型类别：**

| 序号 | 模型类别 | 核心思想 | 典型代表 |
|------|---------|---------|---------|
| 1 | **种子法模型** | 捕获-再捕获，预播"种子"错误估计残留数 | — |
| 2 | **失效率类模型** | 研究程序失效率 | Jelinski-Moranda, Schick-Wolverton |
| 3 | **曲线拟合类模型** | 回归分析研究复杂性/缺陷数/失效率 | 参数方法 + 非参数方法 |
| 4 | **可靠性增长模型** | 用增长函数描述可靠性改进 | Duane, Weibull, Gompertz |
| 5 | **程序结构分析模型** | 根据调用关系形成可靠性分析网络 | Littewood马尔可夫, Cheung面向用户 |
| 6 | **输入域分类模型** | 选取输入域样本点推断使用可靠性 | Nelson模型 |
| 7 | **执行路径分析方法** | 计算逻辑路径执行概率综合可靠性 | Shooman分解模型 |
| 8 | **NHPP模型** | 非齐次泊松过程，预测累计失效数 | Musa指数, Goel-Okumoto, S型 |
| 9 | **马尔可夫过程模型** | 完全/不完全改错的线性死亡模型 | — |
| 10 | **贝叶斯模型** | 利用先验分布和测试信息评估可靠性 | 连续时间离散型马尔可夫链, Shock模型 |

**Musa和Okumoto的分类维度：**
- 时间域：日历时间 vs 执行时间
- 失效数类：有限 vs 无限
- 失效数分布：泊松分布 vs 二项分布

## 9.3 软件可靠性管理

**本质：** 软件工程管理的一部分，以提高和保证软件可靠性为目标，贯穿软件开发全过程。

**各阶段主要活动（考试重点：哪个活动在哪个阶段）：**

| 阶段 | 关键活动 |
|------|---------|
| **需求分析** | 确定可靠性目标、验收标准、管理框架、数据收集规范 |
| **概要设计** | 确定可靠性度量、验收方案、可靠性设计 |
| **详细设计** | 可靠性设计、**可靠性预测**（确定度量估计值） |
| **编码** | 可靠性测试（含于单元测试）、排错 |
| **测试** | 可靠性测试（含于集成/系统测试）、**可靠性建模、可靠性评价** |
| **实施** | 可靠性测试（含于验收测试）、调整可靠性模型、可靠性评价 |

> **易错点：** 可靠性建模和评价出现在**测试阶段**，而非设计阶段。可靠性预测在**详细设计阶段**。

## 9.4 软件可靠性设计 ⭐⭐

**核心观点：保障软件可靠性最有效、最经济、最重要的手段是在设计阶段采取措施。**

可靠性设计三原则：
1. 是软件设计的一部分，不与其他设计原则冲突
2. 以提高和保障可靠性为最终目标
3. 可靠性目标排在**功能度、用户需求和开发费用之后**考虑

### 9.4.1 容错设计技术 ⭐⭐

适用于失效后果特别严重的场合（飞控、空管、核反应堆）。

**三种主要方法：**

| 方法 | 原理 | 关键要点 |
|------|------|---------|
| **恢复块设计** | 选择一组操作作为容错单元，包含多个功能相同、设计差异的程序块文本，故障时用备份替换（**动态冗余**） | 每一时刻一个文本运行，故障时切换备份 |
| **N版本程序设计** | 多个版本对相同输入执行，实行**多数表决** | ①需求说明完全性和精确性 ②设计全过程的**不相关性**（不同人员、算法、语言、工具） |
| **冗余设计** | 在主系统外设计**不同路径/算法/实现方法**的模块作备份 | 相同两套软件互为备份**无意义**（同环境同故障），必须用不同实现 |

> **易混淆点：** 恢复块 = 动态冗余（同一时刻只运行一个），N版本 = 多数表决（同时运行多版本）。

### 9.4.2 检错技术 ⭐

适用于无须在线容错或不能采用冗余设计的地方。

**特点：** 代价低于容错/冗余，但**不能自动解决故障**，需人工干预。

**四个设计要素：**

| 要素 | 说明 |
|------|------|
| 检测对象 | 检测点（易出错/影响大的地方）+ 检测内容（有代表性的指标） |
| 检测延时 | 故障到被检出的时间差，过长则需更换检测方式 |
| 实现方式 | 判断返回结果、计算运行时间、置状态标志位等 |
| 处理方式 | 多数采用"查出故障→停止运行→报警"，也有不停止/部分停止 |

### 9.4.3 降低复杂度设计

- 软件复杂性分为**模块复杂性**（数据流向+程序长度）和**结构复杂性**（模块间关联程度）
- 复杂性超过一定界限时，缺陷数**急剧上升**，可靠性急剧下降
- 设计思想：保证功能基础上，简化结构、缩短代码、优化数据流向

### 9.4.4 系统配置技术 ⭐

**双机热备三种工作模式：**

| 模式 | 别名 | 原理 | 特点 |
|------|------|------|------|
| **双机热备** | Active/Standby | 主机工作，备机监控准备，数据同步写入 | 最常用，但备机资源浪费 |
| **双机互备** | — | 两个独立应用分别在两台机器运行，彼此互为备机 | 对服务器性能要求高 |
| **双机双工** | 集群形式 | 两台服务器均活动，运行相同应用 | 负载均衡 + 互为备份，Web/FTP常用 |

**心跳机制：** 主从系统按时间间隔互发通信信号，主机故障或备机收不到心跳时，系统资源转移到备用系统。

**服务器集群技术：** 一组独立服务器组合为单一系统，透明管理，故障时应用程序自动被另一结点接管。

## 9.5 软件可靠性测试 ⭐

### 9.5.1 测试概述

- 常规测试（划分/随机/覆盖）的结果数据**不能直接用于**可靠性评价，需分析处理后方可使用
- 可靠性测试组成：目标确定 → 运行剖面开发 → 测试用例设计 → 测试实施 → 结果分析
- 最好在**受控的自动测试环境**下由**专业测试机构**完成

### 9.5.2 运行剖面 ⭐

**建模方法：** 采用**马尔可夫链**将输入域编码为状态集，弧表示转换，分配转换概率。

**开发使用模型的两类分层：**
- **用户级分层：** 依赖于谁/什么激励系统（各种用户类型及使用方式）
- **用法级分层：** 依赖于系统能做什么（所有功能）

**概率估计来源（优先级从高到低）：**
1. 现有系统收集的实际数据（最佳）
2. 与用户交谈/观察获得的信息
3. 原型使用与测试分析的结果
4. 领域专家意见
5. 每个弧分配相同概率（最差，无数据时）

> **注意：** 高安全性软件（飞控等），很少使用的代码路径也可能带来灾难性后果，需构造**专门的运行剖面**，补充统计模型之外的测试用例。

### 9.5.3 测试用例设计

- 优先测试**最重要/最频繁**使用的功能
- 采用"强化输入"：比正常输入更恶劣（合理程度的恶劣）的输入

**可靠性测试用例重点考虑的特殊情况：**

| 测试目的 | 描述 |
|---------|------|
| 屏蔽用户操作错误 | 误操作的提示和屏蔽 |
| 错误提示的准确性 | 准确描述用户错误 |
| 错误是否导致异常退出 | 操作错误不应引起系统异常退出 |
| 数据可靠性 | 输入数据有效性检查、过滤、校验和清洗 |
| 异常情况的影响 | 硬件故障/网络故障/模块失效时数据和系统的受影响程度 |

### 9.5.4 测试实施

**关键要求：**
- 测试前检查需求/设计文档一致性和准确性
- **必须是受控测试**，每个用例必须用**相同软件版本**，新版本 = 新测试开始
- 非统计测试应在可靠性测试**之前**完成（之后完成会影响评估准确性）

**可靠性数据四类（可互相转化）：**
1. **失效时间数据：** 发生一次失效所累积经历的时间
2. **失效间隔时间数据：** 本次与上次失效的间隔时间
3. **分组时间内的失效数：** 某时间区内的失效次数
4. **分组时间的累积失效数：** 到某区间的累积失效数

**测试记录必含信息：** 测试时间、测试说明/标识、测试结果（含失效数据）、测试人员。

## 9.6 软件可靠性评价 ⭐

### 9.6.1 评价概述

**评价三方面工作：**
1. 选择可靠性模型
2. 收集可靠性数据
3. 可靠性评估和预测

### 9.6.2 模型选择四个维度 ⭐

| 维度 | 说明 |
|------|------|
| **模型假设的适用性** | 假设是否符合软件系统现状 |
| **预测的能力与质量** | 预测未来可靠性的能力和准确度 |
| **模型输出值能否满足需求** | 当前可靠度、MTTF、故障密度、达标日期、达标成本 |
| **模型使用的简便性** | 数据易收集、模型简单易懂、便于工具使用 |

### 9.6.3 可靠性数据收集

**数据收集五个问题：**
1. 规范不统一，定义混乱
2. 连续性不能保证
3. 缺乏有效收集手段
4. 数据完整性不能保证
5. 数据质量和准确性不能保证

**解决措施：** 及早确定模型、制订收集计划、重视测试数据整理分析、利用数据库。

### 9.6.4 评估和预测

**辅助分析方法：**
- **图形分析法：** 累积失效个数、单位时间失效数、失效间隔时间图形
- **试探性数据分析（EDA）：** 发现循环相关、短期失效急剧上升、失效集中时间段

> **重要结论：** 没有失效无法估计可靠性，不能因为无失效就认为可靠度是1.0。可假设二项式分布做保守估计。

## 高频易混淆对比

### 容错 vs 检错 vs 冗余

| 维度 | 容错设计 | 检错技术 | 冗余设计 |
|------|---------|---------|---------|
| 故障处理 | **自动处理** | 发现并**报警**，需人工干预 | 自动替换备份 |
| 代价 | 较高 | **较低** | 较高 |
| 适用场景 | 失效后果特别严重 | 无须在线容错 | 失效后果严重 |
| 代表方法 | 恢复块、N版本 | 自检、异常处理 | 不同路径/算法的备份模块 |

### MTTF vs MTTR vs MTBF

| 指标 | 全称 | 含义 | 关系 |
|------|------|------|------|
| MTTF | Mean Time To Failure | 平均失效前时间 | — |
| MTTR | Mean Time To Restoration | 平均恢复前时间 | MTTR越短恢复性越好 |
| MTBF | Mean Time Between Failures | 平均故障间隔时间 | **MTBF = MTTF + MTTR** |

### 三种时间度量

| 类型 | 精度 | 说明 |
|------|------|------|
| 自然时间 | 最低 | 日历时间 |
| 运行时间 | 中等 | 启动到结束 |
| **执行时间** | **最高** | CPU实际执行指令时间，度量可靠性最准确 |

## 高频考点速记卡

- ⭐ 软件可靠性定义 = 规定条件 + 规定时间 + 规定功能 + 不引起失效的概率
- ⭐ MTBF = MTTF + MTTR
- ⭐ 执行时间是度量可靠性最准确的时间基准
- ⭐ 容错三种技术：恢复块（动态冗余）、N版本（多数表决）、冗余设计（不同实现）
- ⭐ 可靠性设计是保障可靠性**最有效、最经济、最重要**的手段
- ⭐ 三大建模假设：代表性、独立性、相同性
- ⭐ 双机热备三模式：热备（Active/Standby）、互备、双工
- ⭐ 可靠性测试必须是**受控测试**，用例必须用**相同版本**
- ⭐ 运行剖面建模采用**马尔可夫链**
- ⭐ 软件失效占计算机系统失效的**80%**
