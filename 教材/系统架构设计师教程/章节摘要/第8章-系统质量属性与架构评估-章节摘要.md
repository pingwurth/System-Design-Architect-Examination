## 一、章节概述

本章聚焦两大主题：

## 二、核心知识点

### 8.1 软件系统质量属性

#### 8.1.1 质量属性概念 ⭐⭐

**质量定义**：软件系统与明确地和隐含地定义的需求相一致的程度。

**GB/T 16260.1 六维度**：

| 维度 | 子因素 |
|---|---|
| **功能性** | 适合性、准确性、互操作性、依从性、安全性 |
| **可靠性** | 容错性、易恢复性、成熟性 |
| **易用性** | 易学性、易理解性、易操作性 |
| **效率** | 资源特性、时间特性 |
| **维护性** | 可测试性、可修改性、稳定性、易分析性 |
| **可移植性** | 适应性、易安装性、一致性、可替换性 |

#### 质量属性两大分类 ⭐⭐

| 分类 | 包含属性 |
|---|---|
| **开发期质量属性**（6个） | 易理解性、可扩展性、可重用性、可测试性、可维护性、可移植性 |
| **运行期质量属性**（7个） | 性能、安全性、可伸缩性、互操作性、可靠性、可用性、鲁棒性 |

---

#### 8.1.2 面向架构评估的质量属性 ⭐⭐⭐

评估中普遍关注的**8个**质量属性：

##### 1. 性能 (Performance)
- 系统响应能力：响应时间 或 单位时间处理事件数
- 使用**基准测试程序**进行定量测试

##### 2. 可靠性 (Reliability) ⭐⭐
- 衡量指标：**MTTF**（平均失效等待时间）、**MTBF**（平均失效间隔时间）
- 失效率为常数且修复时间短时，MTTF ≈ MTBF
- 两个方面：
  - **容错**：错误发生时确保正确行为，内部"修复"
  - **健壮性**：保护不受错误使用/输入影响，按定义方式终止（**不是**继续运行）

##### 3. 可用性 (Availability)
- 系统正常运行时间比例
- 用两次故障间时间长度 或 故障恢复速度表示

##### 4. 安全性 (Security) ⭐⭐
- 四大子特性：

| 子特性 | 含义 |
|---|---|
| **机密性** | 信息不泄露给未授权用户 |
| **完整性** | 信息完整准确，防止非法修改 |
| **不可否认性** | 交换双方不能否认发送/接收行为 |
| **可控性** | 对信息传播及内容有控制能力 |

##### 5. 可修改性 (Modifiability) ⭐⭐⭐
- 快速、高性价比地变更系统的能力
- **四个子方面**（高频考点）：

| 子方面 | 关注点 |
|---|---|
| **可维护性** | 问题修复，局部修改，负面影响最小化 |
| **可扩展性** | 新特性扩展，替换构件，需要**松散耦合** |
| **结构重组** | 重新组织构件及关系（如移动到不同子系统） |
| **可移植性** | 适用于多种硬件/软件平台，按硬件软件无关方式组织 |

##### 6. 功能性 (Functionality)
- 系统完成期望工作的能力，需要多构件协作

##### 7. 可变性 (Changeability)
- 架构经扩充/变更成为新架构的能力
- 对**软件产品线**尤为重要

##### 8. 互操作性 (Interoperability)
- 与其他系统交换数据和相互调用的能力
- 需要精心设计的软件入口

#### 易混淆对比 ⭐⭐

| 对比组 | 区别 |
|---|---|
| **可靠性 vs 可用性** | 可靠性：持续无故障运行能力；可用性：正常工作时间比例 |
| **容错 vs 健壮性** | 容错：错误发生时继续运行并内部修复；健壮性：按定义方式终止（不继续运行） |
| **可修改性 vs 可变性** | 可修改性：对系统做变更的能力；可变性：架构变成新架构的能力（产品线层面） |
| **可扩展性 vs 结构重组** | 可扩展性：增加新特性/替换构件；结构重组：重新组织已有构件位置 |
| **性能 vs 可用性** | 性能：响应速度/吞吐量；可用性：正常运行时间比例 |

---

#### 8.1.3 质量属性场景描述 ⭐⭐⭐

> 质量属性场景 = 一种面向特定质量属性的需求，是利益相关者与系统交互的简短陈述

**场景6要素** ⭐⭐⭐：

| 要素 | 含义 |
|---|---|
| **刺激源 (Source)** | 生成刺激的实体（人、计算机系统、其他） |
| **刺激 (Stimulus)** | 到达系统时需考虑的条件 |
| **环境 (Environment)** | 刺激发生的条件（过载、运行等） |
| **制品 (Artifact)** | 被激励的对象（整个系统或部分） |
| **响应 (Response)** | 激励到达后采取的行动 |
| **响应度量 (Measurement)** | 对响应进行度量的方式 |

> 记忆口诀：**源·激·境·品·应·量**

#### 6类质量属性场景速查表

| 质量属性 | 刺激源 | 典型刺激 | 典型响应度量 |
|---|---|---|---|
| **可用性** | 系统内/外部 | 疏忽、错误、崩溃、时间 | 可用时间间隔、故障修复时间 |
| **可修改性** | 用户/开发人员/管理员 | 增删改功能/质量属性 | 影响元素数量、成本、对其他功能影响 |
| **性能** | 用户请求/系统触发 | 定期/随机/偶然事件 | 等待时间、吞吐量、抖动、缺失率 |
| **可测试性** | 开发/测试/用户 | 已完成的设计/代码/系统 | 语句覆盖率、故障概率、测试时间 |
| **易用性** | 最终用户 | 学习特性/有效使用/减少错误 | 任务时间、错误数、满意度 |
| **安全性** | 身份已知/未知的人或系统 | 显示/改变/删除数据、访问服务 | 避开防范时间、检测攻击概率 |

### 8.2 系统架构评估

#### 评估方法三大分类 ⭐

| 方法类型 | 核心思想 | 优缺点 |
|---|---|---|
| **基于调查问卷/检查表** | 设计问卷，利用经验知识 | 缺点：依赖主观推断 |
| **基于场景** | 分析架构对场景的支持程度 | SEI提出，用于SAAM和ATAM |
| **基于度量** | 建立质量属性与度量的映射 | 3步：映射→获取→分析推导 |

---

#### 8.2.1 评估中的重要概念 ⭐⭐⭐

##### 敏感点与权衡点

| 概念 | 定义 | 记忆要点 |
|---|---|---|
| **敏感点 (Sensitivity Point)** | 一个或多个构件（和/或关系）的特性，影响某个质量属性 | 影响**一个**质量属性 |
| **权衡点 (Tradeoff Point)** | 影响**多个**质量属性的特性，是多个质量属性的敏感点 | 影响**多个**质量属性 |

> 经典例子：加密级别是权衡点 — 提高加密级别→安全性↑ 但性能↓

##### 风险承担者 (Stakeholders)

三大类：
- **系统生产者**：架构师、开发人员、维护人员、测试人员、项目经理等
- **系统消费者**：客户、最终用户、应用开发者
- **系统服务人员**：系统管理员、网络管理员、技术支持

##### 场景描述（评估中）

用3方面描述：**刺激(Stimulus)** + **环境(Environment)** + **响应(Response)**

---

#### 8.2.2 三大主流评估方法 ⭐⭐⭐

##### SAAM（软件架构分析方法）

| 项目 | 内容 |
|---|---|
| **提出者** | Kazman 等人，CMU/SEI，1983年 |
| **地位** | 最早形成文档并广泛使用的架构分析方法 |
| **主要质量属性** | **可修改性**（基本特点：任何质量属性都具体化为场景） |
| **评估技术** | 场景技术 |
| **输入** | 问题描述、需求声明、架构描述 |
| **5个步骤** | ①场景开发→②架构描述→③单个场景评估→④场景交互→⑤总体评估 |
| **适用阶段** | 架构最后版本，早于详细设计 |
| **知识库重用** | 不考虑 |

##### ATAM（架构权衡分析方法）⭐⭐⭐

| 项目 | 内容 |
|---|---|
| **基础** | 在SAAM基础上发展 |
| **核心目标** | 考虑**多个相互影响**的质量属性，进行**折中/权衡** |
| **关注的4类属性** | **性能、安全性、可修改性、可用性** |
| **3种场景类型** | ①用例场景 ②增长场景 ③探测场景 |
| **评估技术** | 场景技术 + 定性启发式分析方法 |
| **架构描述** | 基于Kruchten 4+1视图派生的5种基本结构 |
| **4个活动阶段** | ①场景和需求收集→②架构视图和场景实现→③属性模型构造和分析→④折中 |
| **知识库** | 基于属性的架构风格(ABAS) |
| **工具** | **效用树 (Utility Tree)** |

**效用树** ⭐⭐⭐：

```
树根（效用）
  └── 质量属性
       └── 属性分类
            └── 质量属性场景（叶子节点）
```

效用树修剪与排序：
1. 保留重要场景（通常不超过50个）
2. 按**重要性**给优先级：H/M/L
3. 按**实现难易度**给优先级：H/M/L
4. 每个场景得到一个优先级对 (重要度, 难易度)，如 (H, L) = 重要且易实现

##### CBAM（成本效益分析法）⭐⭐

| 项目 | 内容 |
|---|---|
| **基础** | 在ATAM上构建，**ATAM结束时开始** |
| **核心思想** | 从**经济角度**建模，用ROI选择架构策略 |
| **链条** | 架构策略→影响质量属性→带来效用→根据ROI选择 |

**CBAM 8个步骤** ⭐⭐：

```
① 整理场景（选最高优先级1/3）
② 对场景求精（最坏/当前/期望/最好的响应级别）
③ 确定场景优先级（投票→分值）
④ 分配效用（响应级别→效用表）
⑤ 确定架构策略涉及的质量属性及响应级别
⑥ 用内插法确定期望响应级别的效用
⑦ 计算各架构策略的总收益
⑧ 根据ROI选择架构策略
```

---

#### 三大方法对比 ⭐⭐⭐

| 对比维度 | SAAM | ATAM | CBAM |
|---|---|---|---|
| **提出时间** | 1983年（最早） | SAAM之后 | ATAM之后 |
| **核心关注** | 可修改性 | 多属性折中 | 成本效益/ROI |
| **质量属性数** | 主要1个（可修改性） | 4个（性能/安全/可修改/可用） | 继承ATAM结果 |
| **评估技术** | 场景技术 | 场景+定性启发式 | 经济建模 |
| **场景类型** | 直接/间接场景 | 用例/增长/探测场景 | 继承ATAM场景 |
| **知识库重用** | 不考虑 | ABAS | — |
| **关系** | 基础方法 | SAAM的扩展 | ATAM的扩展 |
| **决策工具** | — | 效用树 | ROI排序 |

#### 其他评估方法（了解级）⭐

| 方法 | 核心特点 |
|---|---|
| **SAEM** | 外部属性（用户定义）+ 内部属性（开发者定义），创建评估基础框架 |
| **SAABNet** | 基于BBN（贝叶斯信念网络），表达定性知识辅助评估 |
| **SACMM** | 软件架构修改度量方法，基于图内核计算架构距离 |
| **SASAM** | 静态评估，预期架构与实际架构映射比较，结合PuLSE-DSSA |
| **ALRRA** | 可靠性风险评估，使用FMEA+动态复杂度/耦合度 |
| **AHP** | 层次分析法，定性→定量，多准则决策 |
| **COSMIC+UML** | 基于COSMIC度量评估UML组件图的可维护性 |

### 8.3 ATAM方法架构评估实践 ⭐⭐

#### ATAM 4个基本阶段（9个步骤）

```
阶段1：演示 (Presentation)
  ├─ 步骤1：介绍ATAM
  ├─ 步骤2：介绍业务驱动因素
  └─ 步骤3：介绍要评估的体系结构

阶段2：调查和分析 (Investigation & Analysis)
  ├─ 步骤4：确定架构方法
  ├─ 步骤5：生成质量属性效用树
  └─ 步骤6：分析体系结构方法（找出风险/非风险/敏感点/权衡点）

阶段3：测试 (Testing)
  ├─ 步骤7：头脑风暴和优先场景
  │   └─ 投票公式：票数 = 场景总数 × 30%
  │   └─ 三种场景：用例场景、增长场景、探索性场景
  └─ 步骤8：分析架构方法（重复步骤6，但用头脑风暴结果）

阶段4：报告ATAM (Reporting)
  └─ 步骤9：呈现评估发现
```

#### ATAM实践中的关键输出

- 效用树
- 生成的场景集
- 分析问题集
- 风险和非风险集
- 确定的架构方法

#### 阶段2 vs 阶段3 的区别 ⭐

| 对比 | 阶段2（调查和分析） | 阶段3（测试） |
|---|---|---|
| **质量属性来源** | 效用树 | 头脑风暴投票 |
| **参与者** | 架构师为主 | 更广泛的利益相关者 |
| **场景来源** | 效用树中修剪的场景 | 头脑风暴产生的场景 |
| **投票机制** | 重要性×难易度 | 票数 = 场景总数×30% |

## 三、高频考点速记

### 必记要点

1. **质量属性场景6要素**：刺激源、刺激、环境、制品、响应、响应度量
2. **ATAM关注的4个属性**：性能、安全性、可修改性、可用性
3. **ATAM 3种场景**：用例场景、增长场景、探测场景
4. **效用树结构**：树根→质量属性→属性分类→场景（叶子）
5. **优先级对**：(重要度, 难易度)，用 H/M/L 表示
6. **敏感点 vs 权衡点**：敏感点影响一个属性，权衡点影响多个属性
7. **SAAM主要关注**：可修改性
8. **CBAM核心**：ROI（投资回报率），在ATAM结束时开始
9. **可修改性4子方面**：可维护性、可扩展性、结构重组、可移植性
10. **安全性4子特性**：机密性、完整性、不可否认性、可控性
11. **可靠性2方面**：容错（继续运行）、健壮性（按定义终止）
12. **ATAM 4阶段**：演示→调查和分析→测试→报告

### 易错点提醒

- **容错 ≠ 健壮性**：容错=继续运行并修复；健壮性=按定义方式终止
- **可用性 ≠ 可靠性**：可用性=正常运行时间比例；可靠性=持续无故障能力
- **可修改性 ≠ 可变性**：可修改性=系统级变更能力；可变性=架构变成新架构的能力
- **SAAM不仅限于可修改性**：虽然主要关注可修改性，但也可用于其他属性
- **ATAM效用树的优先级对**：第一个是**重要度**，第二个是**难易度**
- **CBAM不是独立方法**：它在ATAM结束时开始，使用ATAM的结果
- **场景描述用3方面**（评估中）：刺激+环境+响应（不是6要素，6要素是质量属性场景）
- **投票公式**：票数 = 场景总数 × **30%**（不是50%）
