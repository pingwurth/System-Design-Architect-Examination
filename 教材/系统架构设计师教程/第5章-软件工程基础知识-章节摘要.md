# 第5章 软件工程基础知识 - 考前复习笔记

## 章节概述

本章覆盖软件工程全生命周期：从过程模型、需求工程、系统分析与设计、软件测试到项目管理。是考试中**分值最高**的章节之一，几乎每年必考过程模型对比、CMMI等级、耦合内聚、测试方法等知识点。

## 一、软件工程概述与过程模型 ⭐⭐⭐

### 1.1 软件危机与软件工程诞生

- **软件危机**（1968年 NATO 会议首次提出）：进度难预测、成本难控制、功能难满足、质量难保证、维护困难、缺少文档
- **软件工程定义**：将系统化的、严格约束的、可量化的方法应用于软件的开发、运行和维护（IEEE）
- **软件工程过程**：P（规格说明）→ D（开发）→ C（确认）→ A（演进）

### 1.2 过程模型对比 ⭐⭐⭐（高频考点）

| 模型 | 核心特征 | 适用场景 | 主要缺点 |
|------|----------|----------|----------|
| **瀑布模型** | 严格串行、阶段输出→下阶段输入、每阶段有里程碑 | 需求明确且稳定的项目 | 需求难以确定；串行化导致用户等待时间长；变更代价大 |
| **原型模型** | 快速构建原型→用户反馈→修改完善 | 需求模糊、用户无法准确描述需求 | 原型可能被废弃；大型系统原型复杂 |
| **螺旋模型** | 原型+瀑布结合；每轮4步（目标设定→风险分析→开发验证→评审） | 大型、高风险项目 | 成本高、需风险评估专业知识 |
| **RUP** | 用例驱动、以体系结构为中心、迭代增量 | 大型复杂系统 | 重量级过程，过于复杂 |
| **敏捷方法** | 适应性、面向人、迭代增量、拥抱变化 | 需求快速变化、小团队 | 文档少、对人员素质要求高 |

> **关键区分**：
> - 瀑布 = 严格串行，一次性交付
> - 原型 = 快速验证需求（抛弃型 vs 演化型）
> - 螺旋 = 瀑布+原型+风险分析（每轮迭代4部分）
> - RUP = 用例驱动+体系结构中心+4阶段（初始→细化→构造→移交）
> - 敏捷 = 适应性+面向人+短迭代

### 1.3 敏捷方法详解 ⭐⭐

**敏捷宣言核心**：适应性而非预设性；面向人而非面向过程；迭代增量式开发

| 方法 | 关键特征 |
|------|----------|
| **XP（极限编程）** | 4个价值观：交流、朴素、反馈、勇气；小周期迭代 |
| **Scrum** | Product Backlog→Sprint（短迭代）→可交付增量；角色有Product Owner/Scrum Master/Team |
| **水晶系列** | 一组方法族，按项目类型选择合适成员 |
| **FDD（特征驱动开发）** | 5个核心过程：开发整体模型→构造特征列表→计划→设计→构建 |

### 1.4 RUP（统一过程模型）⭐⭐

- **二维模型**：时间维度（4阶段）× 工作流维度（9个核心工作流）
- **4个阶段**：初始(Inception)→细化(Elaboration)→构造(Construction)→移交(Transition)
- **9个核心工作流**：业务建模、需求、分析与设计、实现、测试、部署、配置与变更管理、项目管理、环境
- **核心概念**：角色(Who)、活动(How)、制品(What)、工作流(When)
- **4+1视图模型**：用例视图、逻辑视图、实现视图、进程视图、部署视图

### 1.5 CMMI（软件能力成熟度模型）⭐⭐⭐（必考）

| 等级 | 名称 | 关键特征 |
|------|------|----------|
| Level 1 | **初始级** | 过程随意混乱，依赖个人英雄主义 |
| Level 2 | **已管理级** | 策划、文档化、执行、监督、控制项目级过程 |
| Level 3 | **已定义级** | 企业级标准流程制度化，积累企业资产 |
| Level 4 | **量化管理级** | 建立定量目标，过程性能可预测（与3级的关键区别） |
| Level 5 | **优化级** | 持续改进过程性能，增量式与创新式改进 |

> **记忆口诀**：初管定量优（初始→管理→定义→量化→优化）
> **关键区分**：3级→4级的核心区别 = **过程性能的可预测性**

## 二、需求工程 ⭐⭐

### 2.1 需求层次

| 层次 | 内容 |
|------|------|
| **业务需求** | 组织/客户的高层次目标要求 |
| **用户需求** | 用户使用产品必须完成的任务 |
| **功能需求** | 开发人员必须实现的软件功能 |
| **非功能需求** | 性能、质量标准、设计约束 |

### 2.2 需求工程活动

1. **需求获取** → 2. **需求分析** → 3. **需求规格说明** → 4. **需求确认与验证** → 5. **需求管理**

**需求获取方法**：用户面谈（最常用最有效）、专题讨论会、问卷调查、现场观察、原型化方法、头脑风暴法

### 2.3 需求变更管理 ⭐

- **变更控制过程**：问题分析→变更分析→成本计算→变更实现
- **CCB（变更控制委员会）**：项目所有者权益代表，**决策机构，非作业机构**
- CCB 负责裁定接受哪些变更，但**不提出变更方案**
- 变更策略要点：所有变更必须遵循变更控制过程；未批准的变更不应做设计和实现

### 2.4 需求追踪 ⭐

- **正向跟踪**：需求→后继工作成果（检查每个需求是否有对应实现）
- **逆向跟踪**：工作成果→需求（检查每个设计/代码是否有需求出处）
- 双向跟踪 = 正向 + 逆向
- 工具：**需求跟踪矩阵**

## 三、系统分析与设计 ⭐⭐⭐

### 3.1 结构化方法（SASD）

#### 结构化分析（SA）

- **核心工具**：数据流图（DFD）+ 数据字典
- **DFD 四种元素**：数据流（箭头）、处理/加工（矩形）、数据存储、外部项（圆角框/平行四边形）
- **建模步骤**：明确目标→顶层DFD→第一层分解→层次结构→检查确认

#### 数据字典 5 个组成部分

| 组成 | 描述内容 |
|------|----------|
| 数据项 | 不可再分的数据单位 |
| 数据结构 | 数据之间的组合关系 |
| 数据流 | 数据结构在系统内的传输路径 |
| 数据存储 | 数据停留/保存的地方 |
| 处理过程 | 功能块的说明性信息 |

#### 结构化设计（SD）

- 面向数据流的设计方法，自顶向下、逐步求精、模块化
- **概要设计**：确定系统结构、模块划分、接口和调用关系
- **详细设计**：每个模块的算法和局部数据结构

### 3.2 耦合与内聚 ⭐⭐⭐（必考对比）

**模块耦合（由低到高 7 种）**

| 耦合类型 | 描述 | 耦合度 |
|----------|------|--------|
| 非直接耦合 | 通过上级模块控制 | 最低 |
| 数据耦合 | 参数表传递简单数据 | ↑ |
| 标记耦合 | 参数表传递数据结构 | ↑ |
| 控制耦合 | 传递控制信息 | ↑ |
| 通信耦合 | 共用输入/输出 | ↑ |
| 公共耦合 | 访问公共数据环境 | ↑ |
| 内容耦合 | 直接访问另一模块内部 | 最高 |

**模块内聚（由高到低 7 种）**

| 内聚类型 | 描述 | 内聚度 |
|----------|------|--------|
| 功能内聚 | 完成单一功能，缺一不可 | 最高 |
| 顺序内聚 | 处理元素相关且必须顺序执行 | ↓ |
| 通信内聚 | 处理元素集中在同一数据结构区域 | ↓ |
| 过程内聚 | 按特定次序执行 | ↓ |
| 时间内聚 | 同一时间间隔内执行 | ↓ |
| 逻辑内聚 | 完成逻辑上相关的任务 | ↓ |
| 偶然内聚 | 无关系或松散关系的任务 | 最低 |

> **设计原则**：**高内聚、低耦合**
> **记忆技巧**：耦合从"非直接"到"内容"逐步增强；内聚从"功能"到"偶然"逐步减弱

### 3.3 面向对象方法 ⭐⭐

#### OOA 五层次五活动

- **5层次**：主题层、对象类层、结构层、属性层、服务层
- **5活动**：标识对象类、标识结构、定义主题、定义属性、定义服务
- **两种结构**：分类结构（一般-特殊/泛化-特化）、组装结构（整体-部分）

#### OOD 三种类型 ⭐

| 类型 | 特征 | 示例 |
|------|------|------|
| **实体类** | 永久存储信息，业务领域术语命名，通常有属性不一定有操作 | 学员类、课程类 |
| **控制类** | 控制用例工作，动宾短语转化而来，通常无属性但有方法 | 身份验证器 |
| **边界类** | 系统内外交互接口，既有属性也有方法 | 窗口、报表、通信协议 |

#### OOP 三大特征

| 特征 | 定义 |
|------|------|
| **封装** | 数据和操作组合在一起，隐藏内部细节 |
| **继承** | 子类自动拥有父类的属性和方法（单继承/多继承） |
| **多态** | 同一消息，不同对象表现出不同行为 |

### 3.4 E-R 图（概念结构设计）⭐⭐

- **矩形** = 实体，**菱形** = 联系，**椭圆** = 属性
- 主属性名加下划线
- 多值属性：椭圆外再套实线椭圆
- 派生属性：虚线椭圆
- 弱实体联系：菱形外再套菱形
- **三种联系**：1:1、1:N、M:N
- 联系也可以有属性（如"选修"联系的成绩属性）

## 四、软件测试 ⭐⭐

### 4.1 测试方法分类

| 分类依据 | 类型 | 特征 |
|----------|------|------|
| 是否执行程序 | 静态测试 | 不运行程序，分析检查源程序 |
| | 动态测试 | 运行程序，比较结果 |
| 内部结构了解程度 | 黑盒测试 | 不考虑内部结构，测试功能 |
| | 白盒测试 | 基于内部逻辑，测试路径覆盖 |
| | 灰盒测试 | 介于两者之间 |
| 执行方式 | 人工测试 | 人工驱动 |
| | 自动化测试 | 机器执行 |

### 4.2 测试阶段 ⭐

| 阶段 | 测试对象 | 方法 | 目标 |
|------|----------|------|------|
| **单元测试** | 单个模块 | 静态+黑盒+白盒 | 发现编码错误 |
| **集成测试** | 模块组装 | 白盒+黑盒结合 | 发现接口问题 |
| **系统测试** | 完整系统 | 黑盒为主 | 验证需求满足度 |
| **验收测试** | 交付产品 | 用户参与 | 确认符合合同/用户需求 |

- **Alpha测试**：在开发环境下由用户进行（或模拟环境）
- **Beta测试**：在实际环境中由多个用户进行
- **性能测试**：负载测试（逐渐增加负载）+ 压力测试（找到瓶颈）

## 五、净室软件工程（CSE）⭐

### 核心思想

- 在规约和设计中消除错误，以"净"的方式制作（而非先制作再除错）
- 强调**正确性验证**而非传统测试
- 理论基础：**函数理论** + **抽样理论**

### 四大技术手段

1. **统计过程控制下的增量式开发**
2. **基于函数的规范与设计**（盒子结构：黑盒→状态盒→明盒）
3. **正确性验证**（CSE的核心）
4. **统计测试和软件认证**（使用模型→产生测试用例）

### 缺点

- 太理论化，需要更多数学知识
- 不进行传统模块测试（不现实）
- 带有传统软件工程的弊端

## 六、基于构件的软件工程（CBSE）⭐

### 6.1 构件特征

可组装性、可部署性（二进制形式）、文档化、独立性、标准化

### 6.2 CBSE 过程

系统需求概览→识别候选构件→修改需求→体系结构设计→构件定制与适配→组装构件

### 6.3 构件组装方式 ⭐

| 组装方式 | 描述 |
|----------|------|
| **顺序组装** | 按顺序调用，上一个输出=下一个输入 |
| **层次组装** | 一个构件直接调用另一个构件的服务 |
| **叠加组装** | 多个构件合并创建新构件，原构件不互相调用 |

**接口不兼容**的3种情况：参数不兼容、操作不兼容、操作不完备 → 通过**适配器构件**解决

## 七、软件项目管理 ⭐⭐

### 7.1 进度管理

- **WBS（工作分解结构）**：项目→任务→工作→日常活动
  - 最底层 = **工作包**
  - 一般不超过6层
  - 每个工作包有交付成果

### 7.2 配置管理

- **核心**：版本控制 + 变更控制
- 版本控制追踪文件变更，支持并行开发
- 变更控制管理变更有序进行

### 7.3 质量管理

- **软件质量** = 与明确和隐含需求的一致程度
- **SQA（软件质量保证）**：关注**预防缺陷**而非检查缺陷
  - 事前预防、尽早捕获、作用于过程、贯穿所有活动
- **质量认证**：ISO 9000 和 CMM/CMMI

### 7.4 风险管理

- 目标：**预防风险**
- Boehm体系：风险估计（辨识→分析→排序）+ 风险控制（计划→处理→监督）
- CMU-SEI体系：SRE、CRM、TRM（基于实践的全面风险管理）

## 易混淆点对比

| 对比项 | 区别要点 |
|--------|----------|
| 瀑布 vs 原型 | 瀑布需求明确串行执行；原型需求模糊快速验证 |
| 螺旋 vs 增量 | 螺旋每轮有风险分析和原型；增量是功能的逐步累加 |
| RUP vs 敏捷 | RUP是重量级过程；敏捷是轻量级适应性过程 |
| 抛弃型原型 vs 演化型原型 | 前者验证需求后废弃重来；后者在原型基础上持续完善 |
| 正向跟踪 vs 逆向跟踪 | 正向：需求→实现；逆向：实现→需求 |
| SA vs OOA | SA以数据流为中心；OOA以对象为中心 |
| 耦合 vs 内聚 | 耦合是模块间的联系（要低）；内聚是模块内的联系（要高） |
| Alpha vs Beta | Alpha在开发/模拟环境；Beta在实际环境 |
| SQA vs 测试 | SQA是过程导向预防缺陷；测试是产品导向发现缺陷 |
